# dsh-workspace-memory 设计文档

> 这份文档写给维护者：记录设计取舍、踩过的坑和评测细节（原是仓库根目录的 README，正文未改）。
> 怎么安装、怎么用，见根目录的 [README](../README.md)；当前状态与未验证项见 [HANDOFF.MD](../HANDOFF.MD)。

工作区级持久记忆插件（DeepSeek Harness / Cordis）。设计参考 Claude Code 的 auto-memory 模块，**只做其中的自动记忆层**——指令文件层（AGENTS.md / 路径作用域规则）由宿主已有的注入机制负责，这里不重复造。

## 它解决什么问题

上一代实现（`@yolk_vat-y/dsh-project-memory`）的实测状态：905 个索引文件里 760 个是 MCP 文档转储与第三方源码树，真正在维护的项目一个都没进去；中文查询会返回 `int16` / `sha1` 这类无关符号并打 97–100 分。

**分数不可信比没有检索更危险**——你会误以为「库里没有」而重新推导一遍。这个插件的第一原则是：宁可返回空，不返回噪声。

## 存储布局

记忆有两个按需库，结构完全相同：项目库只在本工作区可见，全局按需库在所有项目里都可见。另有一个每轮常驻的去处，就是全局 AGENTS.md。去向由 `scope`（适用范围）× `load`（加载方式）决定，见「记忆写到哪」。

`memory/` 与 Claude Code 的 auto-memory 完全一致；插件自己的状态放在**它外面**，而且只在真有草稿或历史时才出现：

```
~/.dsh/projects/<编码后的工作区路径>/        ← 项目库（scope: project + load: on-demand）
├── memory/                              ← 只有记忆，与 CC 一模一样
│   ├── MEMORY.md                        # 索引，一行一条，每轮注入
│   ├── no-explanatory-text-in-ui.md     # 一条记忆一个文件，和索引同级
│   ├── hot-reload-local-bundle-generation.md
│   └── pnpm-remove-link-deletes-target.md
└── .memory-state/                       ← 本插件私有；没有草稿/历史时不存在
    ├── pending/                         # 待确认草稿（不论收下后去哪个库，都放在会话所在项目这里）
    └── history/<slug>/<时间戳>.md        # 历史版本（覆盖/删除前留档）

~/.dsh/dsh-workspace-memory/global/       ← 全局按需库（scope: global + load: on-demand）
├── memory/                              # 布局与项目库相同；目录可用 globalMemoryDir 改
└── .memory-state/history/               # 只有历史，没有草稿

~/.dsh/AGENTS.md                         ← 全局常驻（scope: global + load: always），宿主每轮加载；跨项目的做事与表达偏好都在这里
```

**`~/.dsh` 指 DSH 主目录**：环境变量 `DSH_HOME` 非空白时用它（支持 `~` 开头），否则是 `~/.dsh`。插件里所有主目录路径都经 `dshHome()` 这一个入口解析，规则照官方 dsh-home-paths——宿主（AGENTS.md 加载、sessions 目录）按这条规则找主目录，插件若写死 `~/.dsh`，设了 `DSH_HOME` 的用户会读写到另一棵树。写给用户或模型看的文字里，主目录用符号形式：解析结果是默认目录时写 `~/.dsh`，否则写 `$DSH_HOME`，不暴露本机的绝对路径。

全局按需库以包名做命名空间（与插件已有的 `.dsh-workspace-memory-history`、`dsh-workspace-memory-deps` 同形），不在主目录根下另占一个通用名字。

### 向量索引不落盘

语义检索用的 256 维向量**只活在进程内存里**（`vectorStore`），磁盘上没有任何索引文件。

- **首次检索**时懒建，之后全走内存。实测 5 条 77ms、200 条约 650ms；同一进程内第二次 1ms
- 进程重启后重建一次，这是唯一代价
- 换来的是：不再有格式版本、mtime 失效、文件损坏这一整类问题
- `.memory-state/` 只剩草稿与历史版本，**整个目录删掉也只丢草稿和历史，记忆本体分毫不动**

> 为什么不用 DSH 的 `storage` / `storageDomain`：`DomainSpec` 强制要求 `valueSchema: ZodType`，
> 而这个插件是 link 装在工作区里的，Node 按真实路径解析依赖，**`zod` 与
> `@deepseek-ai/dsh-storage-domain` 都解析不到**（和 leanvec 需要专门做回退查找同一个原因）。
> 要用它得先加 `zod` 依赖、再走一次安全的 link 重装，代价大于收益，所以选择内存化。

项目路径按 **DSH 自己的 sessions 目录同一套规则**编码：去掉盘符冒号、分隔符换成单横线、两头包 `--`。
`C:\Users\lenovo\Documents\DSH-Workspace` → `--C-Users-lenovo-Documents-DSH-Workspace--`。

这样 `~/.dsh/projects/` 和 `~/.dsh/sessions/` 用的是同一个键，同一个项目在两棵树下对得上。
（Claude Code 用的是 `C--Users-...`，把冒号也换成横线；这里选了跟宿主一致。）

### 文件名是独立的英文 slug

**索引行要求「英文在前、中文说明在后」，所以文件名必须是英文 slug：**

```md
- [No explanatory text in ui](no-explanatory-text-in-ui.md) — 界面只呈现数据与控件，不加解释性文案
```

- slug 是**独立标识**，不从中文标题派生。改标题**不会**重命名文件
- 只有显式改 slug 才重命名，并删除旧文件（不留两份）
- 撞名自动加 `-2`（**不分大小写**比较——Windows 上 `Docs.md` 与 `docs.md` 是同一个文件），不覆盖别人的记忆
- `memory_remember` 写按需记忆时，标题含非 ASCII 字符却没给可用的英文 slug → **拒写**并返回 `needs-slug`，
  要求模型补一个英文 slug 再调。实测此前真实库里 3 条有 2 条因为模型漏给 slug 落成了中文文件名
- 2026-11-14 起 `slug` 是 `memory_remember` 的**必填**参数：主路径评测里有 6 次写入第一次没给 slug，
  被拒后重试，每次白花一轮。`needs-slug` 的拒写保留，作为模型仍然漏填时的兜底（宿主不替直接注册的工具校验 `required`）
- 抽取草稿、手写文件等其它路径没给 slug 时仍退回标题派生（降级路径）

`memory_remember` 有必填的 `slug` 参数、抽取提示词也会要求模型给英文 slug、面板里可直接编辑（面板拒绝非 ASCII slug）。

> 一处与 CC 的有意偏离：**「项目」取自 DSH 的 `workspaceRegistry`，不是 git repo root。**
> 这个工作区里 `dsh-profile-stats`、`dsh-command-context` 各自是独立 git 仓库，
> 用 git root 会让每个子项目各建一个记忆库；用工作区才能做到「整个工作区共用一个库」。

`MEMORY.md` 照抄 CC 的形态：

```md
# Memory Index

- [Hot reload local bundle generation](hot-reload-local-bundle-generation.md) — 本地 bundle 改完不热更：disable→enable 切一次插件行来换模块代次
- [Profile stats auto npm publish](profile-stats-auto-npm-publish.md) — profile-stats 每次改完自动发 npm（测试 → 升版本 → 提交 → publish → 校验）
```

不写 root / count / 分组标题 / 标签 / id 前缀——那些是噪声，每行宽度应该留给真正的摘要。
链接文字由 slug 机械还原（`-` 换空格、首字母大写），所以**不需要单独维护一个显示名**。

记忆文件本体：

```yaml
---
name: no-explanatory-text-in-ui            # = 文件名
description: 界面只呈现数据与控件，不加解释性文案   # = 索引里破折号后那句
scope: project                             # = 所在的库，只为便于手工查看
type: feedback
status: confirmed
tags: [lesson, README]
paths: []
created: 2026-11-01T07:51:07.279Z
modified: 2026-11-02T01:37:55.091Z
source: user                               # user = 用户说的；agent = 助手自己得出的
evidence: 界面里别加解释性的文字             # 用户原话（source: user 时才有）
evidenceVerified: true                     # 宿主核实过这句证据（source: user 时才有）
title: 界面里不要自行添加解释性说明文字        # 中文标题，只在面板里显示
---
界面里不要出现多余的说明文案。
```

`source` / `evidence` / `evidenceVerified` 由写入时记下，面板只读展示，编辑接口不接受它们；人在面板里收下草稿也不会把 `evidenceVerified` 变成 `true`（收下 ≠ 核实）。旧文件里的 `confidence` 原样保留（只读、不再参与任何判断），新写入的记忆不再有这个字段，见「confidence：只剩旧文件里的只读字段」。

`description` 是索引与正文的公共投影：**显式给了就用给的；正文变了且没给就按新正文重新取一行；正文没变则保持原摘要**，避免只改标签也把摘要冲掉。上限 120 字符（它就是索引那一行）。
自动取行时**跳过标题、代码围栏与分隔线**——正文以 `## 规则` 开头时，以前索引里那一行就只剩「规则」两个字。

frontmatter 是 YAML 的一个子集，读写互为逆运算：

- 值会产生歧义时（换行、首尾空白、`: `、` #`、以 `[ " ' { # …` 开头、空串）序列化器写成 **JSON 双引号串**（也是合法 YAML），普通值仍是裸文本，所以旧文件解析结果不变
- 数组项含 `,` `[` `]` `"` 时同样加引号；`[WIP] Foo [x]` 这种标量不会被误读成数组
- `title` / `description` 是单行字段，落盘前换行一律折成空格；开头的 UTF-8 BOM（记事本另存）会被忽略
- 更新时保留 `hits` / `lastHit` 与所有未知键（手写的、别的工具加的）

`type` 有五种。前四种对齐 Claude Code：`user`（用户是谁：语言、角色、专长、长期偏好）、`feedback`（用户对做法或表达方式的纠正，或确认过的非显然做法）、`project`（代码里看不出的目标、决定、约束与期限）、`reference`（仓库外资源的位置与用途）。第五种 `pitfall`（踩坑经验）是 2026-11-14 加的：踩到并**验证过**的坑，必须写明触发场景与失效条件。

为什么加 `pitfall`：审计里「踩到并验证过的坑」没有对应类型，只能硬塞进 `feedback` 或 `project`，判据也跟着错位——`feedback` 要求用户纠正，`project` 要求是用户说的决定，而坑是模型自己验证出来的。单列一类，「必须验证过、写明失效条件」这道门槛才说得清。各类型的门槛见「什么值得记：提示词分层」。

存进文件的记忆只有这五种（常量 `MEMORY_TYPES`）。`memory_remember` 的 `type` 参数另外接受三个「不是记忆」的取值
`procedure` / `repo-rule` / `docs`（常量 `ROUTED_TYPES`），选了它们工具什么都不保存，只告诉模型该写到哪——见「调用时必须归类」。
存储、面板的类型下拉、编辑接口、抽取都不认这三个取值。

> 局部更新（只改摘要 / 只改 slug）**不会**冲掉 `type`、`tags`、`created`——没传的字段一律沿用原值。
> 早期版本在「没传 type」时会回落成 `project`，已修复并加回归断言。

一条记忆一个 Markdown 文件，插件坏了、被卸了、换编辑器，记忆都还在。
**但请注意**：放进 `~/.dsh` 后记忆不再位于工作区内，**不能用 git 管**——这是 CC 的取舍（机器本地、不进版本库）。

## 注入

每轮进上下文的有两块，放在宿主的两个不同位置：

| 位置 | 内容 | 何时为空 |
|---|---|---|
| 系统提示段 `ctx.systemPrompt.section`（name `workspace-memory`，order 3200，静态） | 写入的行为指引（常量 `MEMORY_SECTION`）：学到东西先判断归宿、什么时候必须处理、什么时候问用户、记忆写的是当时的情况 | 永不为空，也不随轮次变化 |
| 动态 context `ctx.systemPrompt.context` | 项目库索引（`## 本工作区`）、全局按需库索引（`## 所有项目（按需）`）、预取结果（`[相关记忆]`） | 两个库都空、也没有预取结果时返回空串 |

为什么这样分，见「什么值得记：提示词分层」。order 取 3200：首方的工具指引段占 1000–3100，带环境信息的后缀从 10000 起；这一段是「怎么用本插件工具」的静态指引，所以紧跟在首方工具指引之后，仍在可被前缀缓存复用的部分里。

项目库索引上限 **200 行 / 25KB**（先到者为准，照抄 Claude Code 的口径）。全局按需库索引另有上限 `globalIndexMaxLines`（默认 60 行，`0` = 不注入，条目仍可经召回、预取、paths 提示出现）：它在每个项目的每一轮都注入，是跨项目的常驻成本，所以比项目库小得多。超限时**不静默截断**：注入文本末尾追加一行 `[WARNING] N of M memory entries are NOT listed above…`，并为这行预留预算，保证它一定进得去。

> 以前警告是追加在 `MEMORY.md` **文件末尾**的，而注入是从头截断——超限时被截掉的恰好就是警告本身。

**索引过期要说出来。** `MEMORY.md` 是派生物：写入、删除、移库之后重建它，失败（文件被占用、被换成了目录……）只记录、不抛错——
记忆文件已经落盘或删掉了，这时再报失败，调用方会以为整次操作没成而重试，造成重复写入。但失败不能静默：
写入类工具的返回值带 `indexStale` 并在文本里说明「每轮注入的索引还没有这次改动」；`memory_status` 比较索引列出的条目数与记忆文件数，
对不上时明说，并给出 `/memory reindex`。下一次成功的写入或 `/memory reindex` 会把索引补齐。

动态 context 的空小节整节省略；两个库都空、也没有预取结果时返回空串（官方 system-prompt.md：空文本不贡献任何内容）。以前库为空时什么都不注入，模型也就没有任何关于「何时写」的提示——现在这部分在系统提示段里，不依赖库里有没有东西。

`interpolate: false` 是必需的：记忆正文可能含 `{{ }}` 或 `[]`，让它们被当成插值语法解析会把注入搞崩。

注入失败、检索失败、向量构建失败全部 `try/catch` 兜底并降级，**绝不让记忆功能拖垮主对话**。

## 检索：向量 + 关键词混合

本地 embedding 用 `leanvec`（静态嵌入表，dim 256，中文/英文/俄文/代码剪枝，零依赖、不联网、按 token 懒读行）。

融合权重：向量 0.65 / 关键词 0.35。关键词通道对中日韩文字（含假名、谚文）做二元组切分；
拉丁文按词，且**只在词首命中**（`ci` 不再命中 "spe**ci**fied"，`recall` 仍能命中 `memory_recall`）。

真正的闸门是**融合分 `minScore`（默认 0.34）**，由金标集扫描标定，见下文「召回质量怎么衡量」。
`minVectorScore` / `minKeywordScore` 只是前置筛：leanvec 是静态嵌入，任意文本余弦都容易过 0.3，单靠它们等于没有闸门。

向量与文件内容按哈希对账：手改过文件、或新文件还没有向量时，`recall` 会就地增量重嵌，不会继续用旧向量。

检索同时查两个按需库、按分数合并（同分时项目库在前），每条结果带所在的库（`scope`）、最后更新日期 `updated`（取 frontmatter 的 `modified`，没有就取 `created`）和距今天数 `ageDays`。渲染文字里标题行后写一段 `updated 2026-11-05, 9 days ago`，超过 30 天的再加一句 `verify before relying on it`：系统提示段要求模型照着记忆里的文件、命令、配置去做之前先确认它们还在，它得知道这条记忆有多旧。

## 已知限制

**不做跨语言语义桥接。** leanvec 是按语言与字面聚类的静态嵌入表，不是多语言语义模型。实测：中文提问「怎样把服务发布上线前的检查跑一遍」对一条英文记忆只给出 0.45 的相似度，却把同类中文记忆排到了第一。

**记忆尽量与提问同语言书写。** 这条没有在代码里硬撑——测试单独列出并只报告实测值，不假装它做不到的事。

`embed()` 对希腊/希伯来/阿拉伯/泰文返回 `null`（leanvec 未覆盖这些文字），这些内容在建索引时被跳过，检索退回纯关键词。

## 工具

| 工具 | 作用 |
| - | - |
| `memory_remember` | 写一条记忆：按适用范围 × 加载方式定去向，按来源分流（直写或进待确认；常驻一律进待确认），落盘 + 重建索引 + 重建向量 |
| `memory_recall` | 跨两个库混合检索，返回带出处、所在库与更新日期的正文；无匹配时明确说「视为没记录过」 |
| `memory_forget` | 按 id 删除；两个库都有同一个 id 时拒绝并列出两处，要求带 `scope` |
| `memory_status` | 两个库的根目录、条数、索引体积、向量覆盖；索引与记忆文件数对不上时明说并给出 `/memory reindex`；待确认条数；`agentWrites`；当前 agent 最近一次证据核对走的哪一路、结果如何；配置问题 |

`memory_remember` 的参数（必填：`slug`、`title`、`body`、`type`、`source`、`scope`）：

| 参数 | 含义 |
| - | - |
| `slug` | 英文 kebab-case 文件名 |
| `title` | 给人看的标题，可以是中文，不是文件名 |
| `description` | 索引里的那一行（≤ 120 字符），写记忆本身——是规则就写规则 |
| `body` | 正文：规则一两句，再写「Why:」「How to apply:」两行 |
| `type` | 五种记忆：`user` / `feedback` / `project` / `reference` / `pitfall`；三种不保存、只改道：`procedure` / `repo-rule` / `docs` |
| `source` | `user`（用户说的）/ `agent`（助手自己得出的） |
| `evidence` | `source: user` 时给用户说这条记忆的原话，用来核对出处 |
| `scope` | 适用范围：`global`（关于用户本人和协作方式）/ `project`（本工作区的决定、期限、资源、坑；拿不准时选它）。必填，但缺失时仍取 `project`，不拒写 |
| `load` | 加载方式：`on-demand`（默认）/ `always`；`always` 需要 `scope: global`，且总要等用户确认。`type` 为 `user` / `feedback` 且 `scope: global` 时一律按 `always` 处理，不看这个参数 |
| `tags` / `paths` | 标签；这条记忆涉及的真实文件（驱动「碰到文件时提示」） |
| `supersedes` | 要取代的记忆 id；在本库可用唯一前缀，在另一个库里只认精确 id |
| `newMemory` | 只用于按需：查重拦下后，确认这确实是独立的一条 |
| `chapter` / `newChapter` | 只用于常驻：草稿收下时要覆盖的 AGENTS.md 第 N 章 / 确认是新主题 |

`confidence` 参数已删除。每条规则的完整措辞挂在对应参数的说明上（见「什么值得记：提示词分层」），这里只列含义。

返回值里与写入路径相关的字段：`evidenceVerified`（`source: user` 时，这次证据是否核实）、`clearedDrafts`（直写成功后清掉的同意图草稿）、
`replacedDraft` / `sameSlugDrafts`（进待确认时覆盖了哪条草稿、还有哪条同 slug 但意图不同的草稿在队列里）、
`indexStale`（记忆已落盘，但 `MEMORY.md` 重建失败，每轮注入的索引里还没有它）。

`type` 选了改道取值时返回 `reason: 'belongs-elsewhere'` 与 `home`；改道被「更新留在原处」挡下时返回值带 `keptAsMemory: true`（见「调用时必须归类」）。
跨项目偏好被强制常驻、而调用方显式给了 `on-demand` 时返回值带 `loadForced: true`（见「跨项目偏好强制常驻」）。
收下带取代对象的常驻草稿时，结果带 `replaced` / `replacedScope`（旧条已删）、`replacedMissing`（旧条已不存在）或 `replaceFailed`（删除出错，旧条留着）。

宿主不替直接注册的工具校验 schema（官方 tools.md：raw JSON-Schema 工具自己校验输入），`enum` 与 `required` 只是写给模型看的。所以 `execute` 的第一步自己校验：`title` / `body` 必须是非空字符串，`type` 必须在枚举内，`scope` / `load` 给了非法值都拒写，返回 `invalid-argument` 和允许值；`scope` / `load` 缺省或空串取默认值；`source` 缺失或非法按 `agent` 处理。以前非法的 `scope` 会被静默当成默认值，写到模型没想要的去处。

/memory reject <id> 丢弃草稿
/memory forget <id> [project|global]

### 命令卡为什么能默认展开

内置的 `GenericCommandCard` 折叠状态是组件内部 `useState(false)`，没有配置项。
能改的只有扩展点：占用按命令名分发的 keyed slot `conversation.chat.commandview`，
用 `key: 'memory'` 注册自己的卡片，直接铺开。

再用 `ctx.sidebarRight.openTab('memory-list')` 切到记忆面板。这样命令本身不需要任何
「开窗口」的宿主能力。

### 右侧栏记忆面板

> 本节描述的旧面板设计已被 2026-11-15 重设计取代，见 [PANEL.md](PANEL.md) 与 `preview/panel.html`（交互与接口以代码为准）。

`sidebar.right.pane.tab`（keyed、会话级）注册面板主体，tab 类型由
`ctx.sidebarRightTabs.register()` 声明。

**响应式布局**：

- 宽度 ≥ 640px（例如全屏时）：左侧记忆列表 + 右侧详情，左右分栏
- 宽度不足（右侧栏常规宽度）：退化成「列表 → 点一条进入详情」，带「返回列表」

面板内容：

- 顶部：标题、工作区名、刷新
- 分组切换：已确认 N / 待确认 M
- 搜索框：在**标题、摘要、标签、正文**里本地过滤（不走向量检索）
- 列表：两个库的条目都在这里。列表项是标题、摘要（最多两行）、类型徽章；全局按需库的条目另有「跨项目」标签，
  收下后会进全局 AGENTS.md 的待确认草稿有「常驻」标签，并标出「替换第 N 章」（悬停显示章标题）或「新章」；
  带 `supersedes` 的草稿另有「替换记忆 {id}」标签（旧记忆在另一个库时补上所在库），收下之前就能看到会被删掉的是哪一条。
  **不显示置信度百分比**——见「confidence：只剩旧文件里的只读字段」
- 详情：标题 / 类型（本地化标签 + 英文枚举，含「踩坑经验」）/ 适用范围下拉 / 标签 chips（可增删）/ 摘要 / 英文文件名 / 正文
- **适用范围下拉保存后会换库**：改成「跨项目」就把条目移进全局按需库，反之移回项目库（`moveMemory`，源库留档；
  目标库已有同 id 或已满时整体不做）。以前它只改 frontmatter 里的提示字段、旁边写着「不会自动移动文件」
- 来源行（只读）：`source: user` 且 `evidenceVerified` 为 `true` 时显示「用户原话 · “原话”」；`source: user` 但没核实到
  （或旧数据没有这个字段）显示「未核实 · “原话”」；`source: agent` 显示「助手总结」。原话长时折行。
  模型声称「用户说的」不等于真是用户说的——审常驻草稿的人不能把模型编的「原话」当真。没有来源、但文件里有旧
  `confidence` 的条目仍显示原来那行只读置信度
- 正文编辑器带**行号 gutter** 与全屏模式，`textarea` 与 gutter 同步滚动
- 底部：来源文件名（全局库的条目显示「跨项目」）、更新时间、未保存提示、取消 / 保存
- 待确认项：**只读**，显示收下后的去向（适用范围 + 加载方式）与来源；底部换成 **收下 / 丢弃** 两个按钮
  （与 `/memory accept|reject` 同一套宿主函数）。宿主没有「改草稿」的接口，以前允许编辑，改完点收下修改会被静默丢掉。
  收下章节草稿时要覆盖的那一章找不到了，显示「要替换的章节已变动，未写入」（与 AGENTS.md 页签的「已重新读取」分开）
- 失败文案：新增 `partially-saved`（已移库，但其余修改未保存）、`move-failed`（移库未完成，已恢复原状）、
  `move-partial`（移库未完成，两个库里各有一份）。失败响应带 `moved: true` 时同样刷新列表，因为条目已经在另一个库里了
- 收下取代旧记忆的草稿后，若旧记忆没能删除（`replaceFailed`），底部提示「已收下，但旧记忆 {id} 未能删除」，留给人手动处理。
  这条提示和其它底部提示一样约 2 秒后消失，可能来不及看——需要在真实面板里确认
- 标题与摘要是单行字段：回车被拦下（输入法组字中的回车除外），粘贴进来的换行折成空格
- 两个库可能各有一条同 id 的记忆（旧数据），列表的 React key 带上所在的库；发往宿主的保存、删除、写入 AGENTS.md 请求都带上条目的 `scope`
- 中文文案以语言 id `zh` 注册（官方 dsh-client-locale 的基础语言是 `zh` 与 `en`，`zh-CN` 只出现在 `<html lang>` 上）。
  以前注册在 `zh-CN` 下，中文界面查不到、回落到英文

2026-11-14 起的面板改动只做了 `node --check` 与逻辑测试，**视觉没有人看过**，见 HANDOFF 25.7。

「取消」在有未保存改动时会先确认，不会静默丢弃。切换记忆、切换页签、在 AGENTS.md 页签换章或切回记忆库，都走同一个守卫。

`Ctrl/⌘ S` 只在「面板可见、焦点在面板内、当前页签有未保存修改」时接管，否则不拦截宿主别处的快捷键。

保存以宿主回读的记忆为准（改 slug 会换 id，不再按标题去列表里反查）；保存期间切走了，迟到的响应不会写进另一条记忆的编辑器。换会话时面板整体重挂。

### `/memory_list` 的自动打开语义

只在**这次命令真的刚完成**时打开一次，之后不会再自动弹开：

- 判定依据是「卡片首次挂载时结果是否已经存在」——刚敲完时结果是 `null`，随后才出现；
  切回会话或刷新页面时结果已经在，说明只是回放历史，不该打开
- 另有第二道守卫（按命令调用身份记在 `sessionStorage`），防止命令还在跑时重挂载开两次
- 卡片上始终有「打开记忆面板」按钮，任何情况下都能手动打开

> 早期版本用组件内 `useRef` 做「只开一次」的守卫，但它随挂载重置——
> 结果是关掉侧边栏后切会话回来又自己弹开。已改为上面的挂载态判据。

## 数据通道与会话定位

界面与宿主之间走宿主 HTTP 路由，和工作区里 `dsh-profile-stats` 同一条路：

```
GET  /api/dsh-workspace-memory/list?session=<id>            # 两个库的条目（每条带 scope）+ 本项目的待确认草稿
POST /api/dsh-workspace-memory/save?session=<id>            # { id, scope?, patch }；patch.scope 与所在库不同时换库
POST /api/dsh-workspace-memory/accept?session=<id>          # 收下草稿
POST /api/dsh-workspace-memory/reject?session=<id>          # 丢弃草稿
POST /api/dsh-workspace-memory/forget?session=<id>          # { id, scope? } 删除记忆
POST /api/dsh-workspace-memory/promote?session=<id>         # { id, scope? } 把一条记忆搬进 AGENTS.md
GET  /api/dsh-workspace-memory/agents                       # AGENTS.md 概况 + 探测到的编辑器
POST /api/dsh-workspace-memory/open-agents                  # 用指定编辑器打开 AGENTS.md
GET  /api/dsh-workspace-memory/agents/sections              # AGENTS.md 按章切分
POST /api/dsh-workspace-memory/agents/save-section          # { index, expectedTitle, title, body }
POST /api/dsh-workspace-memory/agents/delete-section        # { index, expectedTitle }
POST /api/dsh-workspace-memory/agents/add-section           # { title, body }
```

**所有 POST 必须带 `Content-Type: application/json`**，否则 415。浏览器跨站发出的「简单请求」只能是
`text/plain` / 表单类型，带 JSON 类型就必须先过 CORS 预检——只要宿主不对跨站预检放行，
网页就没法借本机端口改写每轮都会注入的 AGENTS.md。（宿主的 CORS 策略未核实；AGENTS.md 相关路由不要求 session。）

**这些路由没有鉴权**：宿主的网页服务本身不提供（官方 dsh-host-webserver README：「No server-wide authentication or origin policy」），
插件也没有自建。Content-Type 闸门挡的是跨站网页，挡不住本机上能发 HTTP 请求的程序——包括 agent 自己用命令行访问。
这条边界的含义见「局限：防线在哪几层」。

请求里的 `scope` 指条目**现在所在**的库。不带时两个库都找；两处都有同一个 id 时返回 409 `scope-ambiguous`，不猜——猜错就改到或删掉了另一条。

失败统一返回 `{ ok: false, reason, errors }`：

| 状态 | reason |
|---|---|
| 400 | `no-session`、`invalid-id`、`invalid-index`、`invalid-json`、`invalid-scope`、`belongs-in-project-agents`（收下「只在本项目常驻」的草稿）、`same-library` |
| 404 | 记忆 / 草稿不存在 |
| 409 | `section-moved`（章节已被外部改动挪了位置；收下章节草稿时找不到唯一同名章）、`library-full`、`scope-ambiguous`、`target-exists`（换库时目标库已有同 id）、`move-failed`、`move-partial`、`partially-saved`（见下） |
| 413 | `body-too-large`（上限 1 MiB） |
| 415 | `unsupported-media-type` |
| 500 | 未预期的异常 |

AGENTS.md 的章节是按**位置**寻址的。面板写入时带上用户看到的标题 `expectedTitle`，
文件在外部编辑器里被改过、位置对不上时返回 `section-moved`，面板重新读取，不会改到或删到别的章。

**换库不是一个原子操作**（先写目标、再删源），所以失败分三种，各有原因码，面板与模型据此知道条目现在在哪：

| 原因码 | 发生了什么 | 条目现在在哪 |
|---|---|---|
| `move-failed` | 写目标失败，或删源失败而目标已回滚 | 仍在原库，什么都没变 |
| `move-partial` | 删源失败，回滚目标也失败 | **两个库里各有一份**，需要手动删掉多出的那份 |
| `partially-saved` | 换库成功，但随后应用其余字段（标题、正文…）失败 | 在新库里（响应带 `scope` 与 `moved: true`），其余修改没保存 |

以前删源失败时两个库各留一份同 id 的条目，面板按 id 选中会同时高亮两行、第二条打不开；回滚失败时还提示「已恢复原状」。
移库成功后索引重建失败不算移库失败（见「注入」里的索引过期提示）。

**`session` 参数是必需的，不是可选优化。** 2026-11-01 实测踩到：HTTP 请求没有 agent，
若退回 `workingDirectory.defaultDirectory` 会解析到进程默认目录（profile 目录），
面板读到 0 条记忆却返回 200——错得很安静。所以现在宿主用 `sessionId` 反查会话工作目录，
查不到就明确返回 400，绝不猜一个目录去读或写。

## 安全边界

记忆 id 就是文件名，而 id 会从工具参数、HTTP 请求体里原样进来。以前 `memory_forget {id: "../../../AGENTS"}`
会删掉 `~/.dsh/AGENTS.md`——模型一旦被网页或文件内容提示注入，就能触发。现在：

- `isSafeId`：拒绝路径分隔符、Windows 非法字符（仅 ASCII，全角 `：（）` 可以）、控制字符、首尾空白、结尾的 `.`、`.` / `..`、超过 200 字符
- 每处「id → 路径」再做一次包含性检查：解析结果必须平铺在目标目录里，否则不碰任何文件
- 记忆文件、草稿、`MEMORY.md`、AGENTS.md 一律「写临时文件再 rename」，崩溃不会留下半个文件
  （rename 失败——例如编辑器占着文件——时退回直接写）

## 格式闸门

`validateMemoryPatch` 是 UI 编辑唯一的落盘入口，规则集中在一处：

| 字段 | 规则 |
| - | - |
| `title` | 非空，≤ 200 字符，**不能含换行** |
| `body` | 非空，≤ 20000 字符 |
| `type` | 只能是 `user` / `feedback` / `project` / `reference` / `pitfall` |
| `scope` | 只能是 `project` / `global`；与条目所在的库不同时，save 路由先换库，再在新库里应用其余字段 |
| `tags` | 字符串数组，≤ 20 个，单个 ≤ 40 字符，不能含换行、英文逗号或 `]` |
| `slug` | 归一化为小写英文 + 数字 + 连字符；含非 ASCII 字符或归一化后不足 2 字符**直接报错**（以前会静默换成 `memory-<时间戳>`） |
| `description` | ≤ 120 字符（它就是索引那一行），**不能含换行** |
| `paths` | 字符串数组，不能含换行 |
| `confidence` | **只读**（旧文件里的模型自评）；经编辑接口传会被明确拒绝 |

换行之所以要拦：frontmatter 一行一个键，`description: x⏎confidence: 0.1` 以前能直接改写「只读」的 confidence，
`x⏎---` 会把后面的元数据挤进正文。

未知字段直接忽略（`source` / `evidence` 不在可编辑字段里，传了也按未知字段忽略）；任何一条不合法就**整体拒绝**，并逐字段给出原因，前端原样展示。
保存的顺序是「先校验，再换库，再写字段」：校验是纯函数，放在最前面，校验失败时什么都没动。
落盘永远走 `serializeFrontmatter`，所以 **UI 编辑不会让文件格式漂移**——
手改文件会，UI 改不会。

### confidence：只剩旧文件里的只读字段

模型自评的「我对这条有多大把握」和用户的「这条对不对」是两种东西。让用户去填一个概率，
既没有校准依据，也会让人误以为它是质量指标——所以它从来不给编辑。

2026-11-14 起它也不再参与任何判断。以前它管两件事：`memory_remember` 按 `directWriteConfidence` 分流，
自动抽取按 `minExtractConfidence` 丢弃低分候选。审计里 confidence 19 次有 18 次 ≥ 0.9，与这条记忆后来是否被推翻
没有正相关，作为闸门从来没起过作用。现在写入按来源分流（见「记忆怎么进库：按来源分流」），抽取改为核对证据、
把是否核实记下来给人看，两个配置键已废弃。

新写入的记忆不再有这个字段；旧文件里的值原样保留，面板只在没有来源的旧条目上显示它（只读）。

## 记忆写到哪：归宿、适用范围、加载方式

> 2026-11-14 重设计。取代了旧版的两处设计：「`scope` 只是提示、插件没有全局记忆库、插件不写 AGENTS.md」，
> 以及「准入五条（同时满足才进 AGENTS.md）」。审计数据、评测与未验证项见 HANDOFF 第二十五节。

### 起因

审计了两个工作区里带 `memory_remember` 的全部 29 个会话（310 条用户消息、20 次写入调用）：

- 22 个该记的时刻只记下 10 个；漏掉的 12 个里约 9 个是用户对做法或表达方式的纠正，漏记时模型的推理里一次都没考虑过写记忆；
- 记下的 24 条（含历史版本与全局章节）只有 7 条没问题，13 条规则对、但混进了提交哈希、计数、版本号、安装路径，4 条不该记；
- 没有用户信号、模型自行总结的 6 条里，4 条后来被替换、推翻或删除；模型自评的置信度 19 次里 18 次 ≥ 0.9，与后来是否被推翻没有正相关；
- 跨项目规则落进项目库后又在全局重复一份；全局 AGENTS.md 里约 46% 的字节是只在特定场景才用得上的知识。

归结为六个根因：写入没有触发点；「五条全满足」原本是给 AGENTS.md 防膨胀的，被整体搬来管所有写入；踩坑类内容没有对应类型；
靠模型自评置信度分流；`scope` 一个参数同时决定「适用范围」和「加载方式」；工具说明与抽取提示词是两套口径。
本节处理第五条，其余见「记忆怎么进库：按来源分流」「什么值得记：提示词分层」和上文的 `pitfall` 类型。

### 三个依次回答的问题

**1. 归宿**：学到的东西该去哪，以下几处选一处（插件只写最后两处）。

| 归宿 | 放什么 | 谁来写 |
|---|---|---|
| skill | 可重复的多步操作流程 | 模型用文件工具写，先征得用户同意 |
| 项目的 AGENTS.md | 进这个仓库的人和 agent 都要遵守的规则，包括决定仓库里会留下什么的约定（提交说明、代码风格、命名）；只对当前用户成立的项目规则写同目录的 AGENTS.local.md | 同上 |
| README 或仓库文档 | 给人看的项目说明、用法、设计取舍 | 同上 |
| 全局 AGENTS.md | 用户是谁、用户对助手做事和表达方式的长期要求，在所有项目都成立的 | 本插件（`memory_remember`，`scope: global` + `load: always`，进待确认，用户在面板收下后写入） |
| 记忆 | 其余只有助手和这位用户用得上的：代码里看不出的进行中决定与期限、仓库外资源的位置、验证过的坑、还没定成规则的想法 | 本插件（`memory_remember`） |

代码、git 历史、现有文档里已经有的，哪里都不写。拿不准归宿，或者拿不准是长期规则还是只管这一次，模型在回复末尾问用户一句并给出选项。
以前是「拿不准就不记」，现在改为「拿不准就问」：审计显示主要问题是漏记，而且这是有人在场的交互式会话。

**怎么判断**（系统提示段，最终文本以 `MEMORY_SECTION` 为准）：先看形态——可重复的多步流程归 skill，不管只有助手用还是大家都用；
必须遵守的规则以 AGENTS.md 为准，记忆不存第二份；在所有项目都成立的「用户是谁」与做事、表达方式的要求进全局 AGENTS.md；其余只有助手和这位用户用得上的才进记忆。
几个归宿只是并列列出时，模型没有判断依据（代理模型评测里，发布流程、仓库规则、设计取舍都被存成了记忆）。
提示词只是建议；真正让模型在调用时表态的，是 `type` 上的归类（见「调用时必须归类」）；跨项目偏好的去处则由代码强制（见「跨项目偏好强制常驻」）。

**2. 适用范围** `scope`：`global`（任何项目都成立：用户是谁、希望怎么做事和表达）/ `project`（只在本工作区成立：它的决定、期限、资源、坑；拿不准时选它）。
`scope` 是必填参数：代理模型评测里它曾全部落在默认值上——可选、有默认值、又写着「拿不准就选 project」，于是关于用户本人的偏好也落进了项目库。
缺失时仍取 `project`、不拒写（宿主不校验 `required`，不能因为漏填就丢掉一次写入）。

**3. 加载方式** `load`：`on-demand`（默认，召回时出现）/ `always`（每轮常驻）。

后两个问题决定记忆的去向：

| scope | load | 去向 |
|---|---|---|
| project | on-demand | 项目库 `~/.dsh/projects/<key>/memory/` |
| global | on-demand | 全局按需库，默认 `~/.dsh/dsh-workspace-memory/global/memory/`（配置键 `globalMemoryDir`） |
| global | always | `~/.dsh/AGENTS.md` 的一章，一律经用户确认后写入（见「常驻的那一支」） |
| project | always | 不写，返回 `belongs-in-project-agents`，指向 git 根下的 AGENTS.md / AGENTS.local.md |

### 为什么把适用范围和加载方式拆开

旧设计里 `scope: global` 只有 AGENTS.md 一个去处。于是「任何项目都成立、但只在特定场景才用」的知识没有地方放，
只能进每轮常驻的 AGENTS.md——审计时全局 AGENTS.md 里约 46% 的字节就是这类知识，每轮都在为它付上下文成本。
反过来，模型怕 AGENTS.md 膨胀，又会把跨项目规则落进项目库，之后在全局再重复一份。

「对谁成立」和「什么时候需要看到」是两个独立的问题。拆成两个参数后，第四种组合（跨项目、按需）有了专门的库。

**按需不等于看不见。** 按需库的索引每轮注入，每条记忆在索引里占一行 `description`，所以 `description` 参数的要求是「写记忆本身，
规则就写规则」。只在部分场景需要的知识，不管多重要，都留在按需。

> 第五到第八轮曾据此认为「一条怎么做事的规则只要索引行写的是规则本身，就每轮可见，偏好放按需库就够」。
> 这一条已被用户的决定推翻：跨项目的做事与表达偏好一律进全局 AGENTS.md 常驻，见下一节。

### 去处规则：用户的决定

在目标模型上评测时，用户看了全部评测题之后（看 test 组结果之前），对「一条知识该放哪」逐条拍板，插件第九到十一轮据此改写：

| 决定 | 落到插件里 |
|---|---|
| 项目里必须遵守的规则以 AGENTS.md 为准：全员规则写项目 AGENTS.md，只对用户本人成立的写 AGENTS.local.md；冲突以 AGENTS.md 为准 | 项目记忆库**不存规则**，只放进行中的决定与期限、外部资源位置、踩过的坑、还没定成规则的想法；系统提示段写明「规则不往记忆里存第二份」 |
| 决定仓库里会留下什么的约定（提交说明、代码风格、命名）算这个仓库的规则 | 写项目 AGENTS.md，不进记忆 |
| 所有跨项目的做事与表达偏好进全局 AGENTS.md 常驻 | `scope: global` + `load: always`；第十轮起由代码强制 |
| 写进全局 AGENTS.md 仍要用户在面板确认 | 常驻一律待确认不变 |
| 只纠正这次结果的、话里带「这次」的，都不记 | 系统提示段写明「这次」不记；只纠正结果（算错了、写错了）时改对就行，不要自己归纳出一条做法去记 |

这推翻了此前「偏好放按需库就够、省下常驻开销」的设计倾向。**以用户的决定为准**：不要为了省常驻开销再把偏好挪回按需库。
常驻的代价仍然在——全局 AGENTS.md 每轮注入所有项目，所以 `maxAgentsBytes` 硬限与「常驻区只放规则与指针」照旧适用，而且每一条都要用户收下。

### 跨项目偏好强制常驻

`type` 为 `user` / `feedback` 且 `scope: global` 的写入，按定义就是「用户在所有项目都成立的要求」，所以**由代码判定去处**，
不再交给模型选：不论 `load` 给了什么，一律按常驻处理（`resolveLoad`，类型清单 `ALWAYS_TYPES`），走常驻分支进待确认；
模型显式给了 `on-demand` 而被覆盖时，返回 `loadForced: true`，文本里说明原因。自动抽取用同一条规则。`scope: project` 的不受影响。

为什么不靠提示词：目标模型评测里，模型多次在回复里说「已记到全局偏好」，却把 `load` 留在 `on-demand` 或干脆没给——条目进了按需库，
下次会话不会自动生效。与「调用时必须归类」同一个道理：去处能由代码判定的，就不让模型凭措辞记住。

### 常驻草稿取代旧条

强制常驻之后出现了一个新问题：要更新一条已经在按需库里的旧偏好时，新内容进了全局 AGENTS.md，旧条却还留在按需库，
同一条偏好有了两个出处（第十轮复现过）。所以常驻写入也接受 `supersedes`：

- 写入时照按需写入的规则解析被取代的条目（`lookupSuperseded`：两个库的精确 id 优先、本库可用唯一前缀、跨库只认精确 id），解析不到照样拒写；
  此时**什么都不动**，只把旧条的 id 与所在库（`supersedesScope`）记进草稿；
- 用户在面板收下时，**先写 AGENTS.md 章节，写成功后再**把旧条归档删除（`retireSupersededMemory`，删除前留历史版本）；
- 丢弃草稿、或章节写入失败（`section-moved`、`agents-full` 等）时旧条不动；
- 收下前旧条已被删掉、改名或搬走：只写章节，返回 `replacedMissing`，不去别处猜一条同名的删；删除本身出错不让收下失败（章节已写，
  再报失败会让人重复收下），返回 `replaceFailed`，旧条留着由人处理。

面板的待确认页用「替换记忆 {id}」标出收下会删掉的旧记忆；收下后旧记忆没能删除时，底部会提示（见「右侧栏记忆面板」）。

### 为什么插件不直接写项目的 AGENTS.md

`project + always` 的归宿是项目自己的 AGENTS.md，但插件不写它，只在拒写时告诉模型文件在哪、该怎么做：

- 插件写 AGENTS.md 的章节协议会统一重排编号，会打乱人手工编排的项目 AGENTS.md；
- 项目 AGENTS.md 是共享、进版本控制的文件，改动应当由用户看过。所以模型要先说明想写什么、为什么，用户同意后再用文件工具写（用户明确要求时直接写）；
- 拒写文本里的路径照宿主的加载规则算：宿主只从「会话工作目录往上最近一个含 `.git` 的目录」往下加载项目指令（官方 dsh-agent-instructions 的 findProjectRoot），
  所以指向那个目录下的 AGENTS.md，而不是记忆库所用的已注册工作区根——指向别处等于让模型写一个宿主不加载的文件。
  只对当前用户成立的项目规则写同目录的 AGENTS.local.md（宿主同样加载，不进版本控制）；
- 如果那其实是用户的个人偏好而不是项目规则，拒写文本也给出另外两条路：改成 `scope: "global"`，或改成 `load: "on-demand"` 记进本工作区的库。

skill 与 README 同理：插件只负责「记忆」这一个归宿，其余三个由模型用文件工具写。

### 调用时必须归类：三个不保存的 `type`

`memory_remember` 的 `type` 除了五种记忆，还有三个「不是记忆」的取值：

| `type` | 是什么 | 返回的 `home` | 返回文本给出 |
|---|---|---|---|
| `procedure` | 可重复的多步操作流程 | `skill` | 项目级 skill 的位置（git 根下的 `.dsh/skills/<name>/SKILL.md`）、用户级的位置、frontmatter 格式（`name` 与目录名一致、`description` 一句话） |
| `repo-rule` | 这个仓库里所有人都要遵守的规则 | `agents` | git 根下的 AGENTS.md（是否已存在）、只对当前用户成立的写 AGENTS.local.md；若其实是个人偏好，改用 `feedback` / `user` 重来 |
| `docs` | 项目是什么、怎么用、为什么这样做 | `readme` | git 根下的 README.md（是否已存在），较长的内容可进仓库文档 |

选了它们，工具**什么都不保存**——不进库、不进待确认、不做证据核对、不查重，也不因为缺 slug 之类先返回别的拒写——
返回 `written: false`、`reason: 'belongs-elsewhere'` 和 `home`，文本写明该写到哪、这是共享文件要先向用户提议（用户已明确要求时直接写），
并且不要再往记忆里存一份。自动抽取遇到这三类同样跳过并计数（抽取是离线的，没法向用户提议）。

**为什么用这个机械手段，而不是继续改措辞。** 三版提示词下，用户没明说去处的归宿场景在代理模型上始终不稳，两次采样之间会翻转。
而模型判错时，自己在正文里写着「所有 agent 都必须遵守」，然后仍存成 `type: project`——它知道答案，只是调用时没被要求表态。
把归宿判断放进一个必填参数的取值里，模型每次调用都得回答「这是什么」，答错的代价也从「多了一条错放的记忆」变成「被告知去处」。
顺带的好处：skill 的目录与格式这类细节只在用到时由工具给出，不必常驻在每轮的提示词里（官方 tool-design.md：先给最少的上下文，详细说明按需加载）。

**更新留在原处。** 改道引入过一个缺陷：用户更新一条已有记忆（例如分支规则变了），模型带着 `supersedes` 却把类型选成了 `repo-rule`，
工具改道后什么都没存，旧记忆原样留在库里，成了与用户最新说法相反的错误记忆。所以规则是：`type` 是改道取值、同时 `supersedes`
能解析到一条**确实存在**的记忆时，不改道，按被取代那条记忆自己的类型走正常写入（加载方式固定为按需），返回值带 `keptAsMemory: true`，
文本说明为什么没改道，并提醒「若它真该写进仓库，先向用户提议，写好后删掉这条记忆」。`supersedes` 解析不到时照旧改道。
解析规则与正常写入相同：两个库的精确 id 优先，本库的唯一前缀也算，其余都算解析不到。

被改道之后模型会不会真的向用户提议，目前没有任何验证（代理模型评测是单步作答，看不到工具返回），见 HANDOFF 25.10。

### 借鉴了谁（只借鉴设计，不引入任何库）

| 来源 | 借鉴 | 不借鉴 |
|---|---|---|
| Claude Code 的自动记忆 | 索引常驻、正文按需；一事一文件；类型封闭；明确的「不记什么」；更新已有条目而不是重复新建；正文写「为什么 / 怎么用」；读到记忆时提示它是当时的情况 | — |
| mem0 | 「写入准入决定噪声」这条教训（其 issue #4573：审计一万多条记忆，绝大部分是垃圾），落到准入规则与证据规则上 | 由 LLM 判定增删改 |
| 「证据须为用户原话」的做法（另一个项目里验证过） | 用代码核对出处，同时挡住幻觉和「助手复述后又被记成新记忆」的回路 | 「助手的结论一律不作来源」：编码场景里验证过的坑有价值，所以改为进待确认 |

## 面板与全局 AGENTS.md

> 本节描述的旧面板设计已被 2026-11-15 重设计取代，见 [PANEL.md](PANEL.md) 与 `preview/panel.html`（交互与接口以代码为准）。

面板可以把一条记忆提升为全局 AGENTS.md 的一章，也可以直接打开、编辑 AGENTS.md。这与 `memory_remember` 的 `load: always` 写的是同一个文件。

### 搬到全局：`POST /promote`

全局按需库里的条目（以及项目库里 frontmatter 写着 `scope: global` 的旧条目——那是旧版「该挪去全局」的提示）
会出现「写入 AGENTS.md」按钮。点击后（**先弹确认**）：

1. 往 `~/.dsh/AGENTS.md` 追加一节 `## <标题>` + 正文
2. 从条目所在的库里删除这条（`deleteMemory` 会先留历史版本，可回退）

它会写用户手写的全局文件，所以有四道保护：

- 标题已存在 → 返回 `already-present`，**绝不重复追加**（按去掉编号后的标题比较）
- 只追加，不改写任何已有内容；受 `maxAgentsBytes` 约束，写前留档——和面板「新增章」走同一个 `appendAgentsSection`
- 删除走带留档的那条路径
- 只有跨项目的条目才允许搬（全局按需库里的，或带旧版 `scope: global` 提示的），避免把项目内知识污染成全局规则；
  「只在本项目成立却要常驻」的归宿是项目自己的 AGENTS.md，不是这个全局文件

> 以前 promote 自己拼字符串写文件：同名检查用的是不带编号的标题（实际标题都带 `N.`，永远匹配不上），
> 也不查字节上限、不留档。现在三道保护都由同一个函数承担。

> AGENTS.md 是**每轮都注入**的。搬太多进去会持续占用上下文，
> 建议只放真正跨项目、且长期稳定的规则。

### 打开 AGENTS.md

面板顶部显示 `AGENTS.md · 体量 / 节数`，旁边是「打开方式」下拉和「打开」按钮：

- 探测顺序：配置 `editorExe` → Windows `App Paths` 注册表 → 常见安装路径
- 目前识别 Typora、VS Code、Cursor，另有「系统默认」兜底
- **不写死某个编辑器**：Typora 常装在非默认盘（本机在 `D:\Program Files`），
  所以注册表优先，而不是猜路径
- 选择结果记在浏览器 `localStorage`，下次沿用

### 交互反馈

`hover` / `active` / `focus-visible` 内联样式写不了，所以 `apply` 里挂一份真实样式表

## 记忆怎么进库：按来源分流

`memory_remember`（模型主动记）**不是无脑入库**，而是按**来源**分流：用户亲口说的、证据核实过的（`source: user`）按需记忆直接生效，
模型自己得出的（`source: agent`）默认先给人看；**常驻的不论来源，一律等用户确认**。

| source | 证据 | load | 结果 |
|---|---|---|---|
| 任意 | — | always | **一律**进待确认，`always-needs-user`（`agentWrites: direct` 也不例外） |
| user | 核实 | on-demand | 直写 |
| user | 未核实 | on-demand | 进待确认，`evidence-not-found` |
| agent | — | on-demand | `agentWrites: direct` 时直写；否则（默认 `review`）进待确认，`agent-review` |

`source` 缺失或非法按 `agent` 处理：说不清是谁说的，就当模型自己得出的。`rememberRoute()`（已导出、有测试）就是这张表。
`project + always` 在分流之前就拒写（见「记忆写到哪」）；常驻的章节协议（第 N 章 / 标题同名 / `newChapter`）在入队前校验；
按需写入的查重与条数上限也在分流之前，进待确认的写入同样会被拦下。

**为什么常驻一律进待确认**：全局 AGENTS.md 每轮注入所有项目，写错影响面最大；而证据核对只能证明「这句话出自用户」，
证明不了用户想把它变成处处常驻的规则。第一次审查指出：用户回一句很短的话，模型就能拿它当证据，把任意内容直写进全局 AGENTS.md。
所以记忆工具不再直写这个文件——参数说明（`LOAD_RULE`）里也写明「always 总要等用户确认」。跨项目偏好按用户的决定进这里，同样先进待确认。

返回文本分清两种结果：直写成功的末尾是 `It is active now; no review is needed.`，进待确认的是
`Tell the user it is waiting in the memory panel.`。主路径评测里模型曾在直写成功后对用户说「在面板里等你确认」，
原因是工具说明里写着那句话；现在该怎么对用户说只由返回文本给出。

### 为什么用来源，而不是置信度

审计里 confidence 19 次有 18 次 ≥ 0.9，与这条记忆后来是否被推翻没有正相关，待确认队列从来没被用过——分流等于不存在。
而没有用户信号、模型自行总结的 6 条里，4 条后来被替换、推翻或删除。「谁说的」比「模型觉得自己有多大把握」可靠，
而且可以用代码核对。

模型自己得出的内容不在对话里再问一遍，直接进待确认：人在面板里收下或丢弃一次就够了，不做两次确认。

### 证据核对

`source: user` 时总会核对一次（常驻写入也做，结果只用于记录），结果存进 `evidenceVerified`——草稿与正式记忆都存，
面板据此区分「用户原话」与「未核实」，人点了「收下」也不会把它改成 `true`。**「核实」要两条都满足：**

1. **出处**：证据能在用户自己发的消息里核对到。
2. **相关**：证据确实在说这条记忆（`evidenceRelates`），而不是拿一句无关的回复当证据。

核对只回答「这句话出自用户、而且与这条记忆沾边」，不判断语义——它能做到和做不到的，见下面「局限：防线在哪几层」。

- **只认明确标记为用户的消息。** 宿主注入的上下文（子目录 AGENTS.md、skill 内容、文件变更通知、每轮的 runtime-context 快照——
  本插件的记忆索引就在里面）在会话里也是 `user/message`，只能靠 `source.kind === 'user'` 区分（官方 session.md）。
  **没有 `source` 字段的消息不算**：真实宿主里 `source` 是必填，来路不明的消息放行，等于让任何不带标记注入的上下文都能给证据作保（以前放行过，第一次审查后改掉）。
  迟到的提问回答（`user-question-reply`）不算，那里常是模型自己写的选项。文本里**任意位置**的 `<system-reminder>…</system-reminder>`
  块都先剥掉——宿主会把提醒附在用户消息的同一个文本块里，不一定在开头。口径只有 `humanTextOf` 一份（缓存、快照回落、预取查询共用）。
- **取数顺序。** 先用 `agent/pre-step` 时收进进程内缓存的人写消息（每个 agent 最近 200 条，单条截断到 20000 字符，
  `agent/disposed` 时清掉）；没通过再回落到 `session.snapshotEvents()`。`snapshotEvents()` 已被官方标为弃用
  （「new calls are prohibited」），回落只为一种情况：DSH 重启后恢复的会话，早先的用户消息不在进程内缓存里。
  宿主将来移除这个接口时，回落的结论是「未通过」（进待确认），不报错。官方的替代 `ctx.sessionProjections` 要求 Zod 类型的
  `stateSchema`，link 安装下拿不到，所以没用。`memory_status` 显示当前 agent 最近一次核对走的哪一路（`prestep-cache` / `snapshot-fallback`）
  和结果；核对状态按 agent 分开记，多个会话不串（以前是进程级的一个变量）。
- **出处的比对。** NFKC、小写、去掉全部空白与标点符号后精确匹配。先按省略号切段，各段必须**按顺序**落在**同一条**用户消息里
  （跨消息拼接能拼出用户从没说过的话），每段至少 2 字、合计至少 4 字。精确不过时，归一化后 10–500 字的段允许与某个
  连续片段有不超过长度一成（向下取整）的编辑距离（Sellers 近似子串匹配），更短与更长的段仍须精确出现——主路径评测里模型抄原话
  漏了一个字，核对不过，白进了一次待确认。不用「公共子序列占比」这类度量：它能被长消息里分散各处的字符凑出来。
- **近似匹配的上限。** 核对是在工具调用里同步算的。第一次审查实测「1000 字证据 × 200 条长消息」要数秒，缓存加快照回落近 10 秒，整个回合都卡着。
  所以超过 500 字的段只做精确匹配，近似匹配只看最近 50 条用户消息、每条前 20000 字符；精确匹配不受这些上限。
  理由是抄错一两个字只会发生在短句上，长证据要么原样抄对，要么就不是原话。
- **相关的判断**（`evidenceRelates(evidence, [标题, 摘要, 正文])`）：两边做 NFKC、小写后，共有 ≥ 2 个不同的中日韩二元组
  （同一段连续文字里相邻的两个字），或共有 ≥ 1 个长度 ≥ 3 的 ASCII 字母数字词（`git`、`npm` 这类短技术词也算）；
  证据归一化后不足 6 个字的短纠正，门槛降为 1 个二元组。比对范围包括正文，因为正文按要求写「Why:」，通常会引用用户的话。
- **返回文本保持中性。** 没核对到时只说「没在用户消息里核对到」，不区分「找不到原话」与「与这条记忆不沾边」，也不说怎样才算沾边——
  说了就是在教模型把用户的话抄进标题来绕过。没给证据单独一句。

### 待确认队列

三个来源：`memory_remember` 进待确认的写入（三种原因见上表）、手动 `/memory extract`、自动抽取（默认关闭）。

- 草稿永远放在会话所在项目的 `pending/` 里；收下时按草稿记录的 `scope` + `load` 落到对应去向。
  `project + always` 的草稿拒收（`belongs-in-project-agents`），草稿留在队列里由人丢弃（面板只能收下或丢弃，不能改草稿）。
  旧草稿没有 `load` 字段时，`scope: global` 按写下它时的含义落进 AGENTS.md。
- **章节草稿按章标题定位。** 「更新第 N 章」的常驻草稿存下章号和那一章当时的标题（`chapter` / `chapterTitle`）。
  收下时在当前 AGENTS.md 里找标题相同的章（去掉编号前缀与首尾空白、做 NFKC 后比较），唯一命中就覆盖那一章，不管它现在是第几章；
  找不到（被删或改了名）或有多个同名章才返回 `section-moved`，什么都不写，草稿留着。章号只供面板显示「替换第 N 章」。
  第一次审查前草稿不存章号，收下一律按新章追加，AGENTS.md 里出现原章与合并版两份；修成按章号定位后，复审又发现
  删掉前面任意一章、编号整体前移，草稿就永远收不下了。
- **覆盖与清理都按「意图」判断**（`draftIntent`：去向 `scope` + `load`、要取代的 `supersedes`、章号、`newChapter`）：
  - 入队时，队列里已有同 slug **且意图相同**的草稿就覆盖它（返回 `replacedDraft`）：审计里 20 次写入有 14 次在 4 个主题上反复改写，
    直写有查重兜着，进队列的却会堆出一串同主题草稿。同 slug 但意图不同的草稿两条都留，返回文本里点名另一条（`sameSlugDrafts`）——
    只看 slug 时，一条「常驻 + 取代 X」的草稿会被同 slug 的普通草稿整个盖掉，去向和要取代的条目都丢了；
  - 直写成功后，清掉同 slug **且意图相同**的旧草稿（返回 `clearedDrafts`）：典型情形是第一次证据没核对上进了待确认，
    重试直写成功，旧草稿还留着，之后有人收下就多出 `xxx-2`。要取代 X 的草稿不会被一次不带 `supersedes` 的写入清掉。
  - 两条同 slug、意图不同的草稿都被收下时，库里会出现带 `-2` 后缀的第二条——这是已知局限，返回文本的点名就是为了让人别两条都收。
- 收下 / 丢弃只留给用户（面板按钮与 `/memory accept|reject`），没有让 agent 自己收下草稿的工具或参数
  （官方 user-actions.md：用户确认类动作只留给用户）。HTTP 路由没有鉴权这一点见下节。

**删除入口**：面板详情底部有「删除」按钮（红色描边，与保存按钮并列），
也可用 `/memory forget <id> [project|global]`（支持前缀）。两处都走 `deleteMemory`，删除前留历史版本可回退。
之前只有模型能调 `memory_forget` 工具，人删不掉——记忆直接入库时这个缺口很致命。

### 局限：防线在哪几层

证据核对的定位是**出处核对，不是语义校验**。两次独立审查之后，它能做到和做不到的如下（数字是实测的）：

- **只管出处，不管语义。** 模型截取用户否定句的后半段（「不要每次都提交到主分支」只取后半句）、用省略号跳过否定词、
  近似匹配里一字之差翻转了意思，字面上仍是用户说过的字，都可能通过。代码判断不了；也不该用否定词黑名单之类的办法去补，
  误伤和漏网都会很多。
- **相关性判断是字面的。** 用 22 条真实纠正样例实测：正文引用了用户原话时误判 0 条；标题、摘要、正文全部改述时误判 3 条
  （都是很短的纠正），误判的后果只是进待确认。完全无关的回复当证据，5/5 被拦下；但把无关回复抄进标题或摘要，6/6 能绕过。
  它挡的是「拿一句『好的，继续』当证据写进任意内容」，证明不了「证据确实陈述了这条规则」。
  （第一次审查后曾只比标题与摘要、门槛偏高，复审实测约两成真实纠正被误判，又能被抄标题绕过，于是放宽并重新定位成现在这样。）
- **HTTP 路由没有鉴权**（见「数据通道」）。agent 若用命令行访问这些路由，理论上能自己收下草稿；它的文件工具本来也能直接改 AGENTS.md。
  插件保证的是「**记忆工具**不直写 AGENTS.md」，不是「agent 无论如何写不了」。
- 斜杠命令展开的文字、子 agent 的创建提示，来源标记可能与用户手敲的消息相同，离线无法确认会不会被当成用户原话。
- 近似匹配加了上限之后，极端输入下仍约 1 秒。

**为什么仍然这样做。** 证据核对的价值在于用代码挡住两类问题：模型凭空编「用户说过」，以及助手复述的话被当成用户原话、
再记成新记忆的回路。它不负责判断内容对不对——那是人的事。所以防线分三层，核对只是其中最便宜的一层：

1. **常驻一律由用户确认。** 影响面最大的去处（全局 AGENTS.md），记忆工具没有直写的途径，与证据核对的结果无关。
2. **未核实的在面板上明示。** 核不上的证据照样存下，但来源标成「未核实」，人审草稿时不会把模型编的「原话」当真。
3. **提示文案不教模型怎么绕。** 拒写与待确认的文本只说结果，不说判据细节。

剩下的按需写入，错了的代价是多一行索引、一次召回；人在面板里能看到证据原文，随时删除，删除前留历史可回退。

## 面板里的两个页签：记忆库 / 全局 AGENTS.md

> 本节描述的旧面板设计已被 2026-11-15 重设计取代，见 [PANEL.md](PANEL.md) 与 `preview/panel.html`（交互与接口以代码为准）。

面板顶部有「记忆库 | AGENTS.md」切换：

| 页签 | 数据 | 能做什么 |
|---|---|---|
| 记忆库 | 项目库与全局按需库的全部条目，加本项目的待确认草稿 | 审核待确认（收下/丢弃）、编辑、改适用范围（换库）、删除、写入 AGENTS.md |
| AGENTS.md | `~/.dsh/AGENTS.md` | 直接改章：编辑标题与正文、增删章、编号自动重排 |

**章节切分规则**：`##` 成章，其下的 `###` 属于该章正文；`#` 一级标题算文档前言、不参与编辑。
所以删一章会连同它的子节一起删，不会留下孤儿标题。

**代码块**：围栏代码（```` ``` ```` / `~~~`）里的 `#` / `## ` 是代码，不参与切章、编号与标题下沉。

**编号**：写入后统一重排为 `## N.` + `### N.M`，删章不留断号；标题里即便带旧编号也会被剥掉重排。
只有 `N.` / `N.M` 这种形态算编号：`### 5 Whys`、`### 2024 roadmap` 原样保留。没改动的章逐字节保留，原文件的换行风格（CRLF/LF）也保留。

**安全**：每次写盘前把原文件复制到 `~/.dsh/.dsh-workspace-memory-history/agents/`（保留最近 20 份）。
超出 `maxAgentsBytes` 时拒写，但**让文件变小的编辑始终允许**——否则超限之后连删一章都删不掉。

**做不到的**：DSH 的指令加载器（`@deepseek-ai/dsh-agent-instructions`）不对外暴露服务，
所以**无法权威判断**某个文件是否被字节预算截断——面板只能显示文件大小。

## 常驻的那一支：全局 AGENTS.md（`load: always`）

`scope: global` + `load: always` 写进 `~/.dsh/AGENTS.md` 的一章，**所有项目每轮注入**。
不论来源、不论证据，**一律进待确认**，由用户在面板里收下后才写入（为什么见「记忆怎么进库」）。
`type` 为 `user` / `feedback` 且 `scope: global` 的写入不论 `load` 给了什么都走这一支（见「跨项目偏好强制常驻」）；
带 `supersedes` 时，收下后旧条被归档删除（见「常驻草稿取代旧条」）。

章节协议在**入队之前**校验（`planAgentsChapter`，只判断不写）：先按标题精确匹配，同名就记成「更新那一章」；
`chapter: N` 指定要覆盖的章（不存在返回 `chapter-not-found`）；**都不匹配时不会自动记成新章**，必须由调用方确认——见下面的「语义重复」。
通过后草稿记下章号与那一章当时的标题，收下时按标题找那一章（见「待确认队列」）。字节预算不在入队时判，以收下那一刻为准。
人已经按过「收下」，收下时不再二次确认语义重复。

### 语义重复：不自动判断，强制确认

同一个主题换个说法，字面相似度会落在很宽的区间。实测（以本机 11 章标题为基准）：

| 新写法 | 相似度 |
|---|---|
| 换语序 | 0.90 |
| 缩短 | 0.47 |
| 口语化 | 0.23 |
| 换词 | 0.24 |
| **不相关（假阳性）** | **0.35** |

真重复 0.23–0.90、假重复 0.35，**区间重叠**——任何阈值都会两边出错，所以不做自动合并，
改为在协议上**逼出判断**：

| 调用 | 行为 |
|---|---|
| `chapter: N` | 覆盖第 N 章（新旧内容由调用方自己合并） |
| 标题精确同名 | 更新那一章 |
| `newChapter: true` | 显式声明新主题，追加 |
| 以上都不满足 | **拒写**，返回现有章标题清单 |

### 常驻区只放规则与指针（渐进式加载）

AGENTS.md **每轮请求都会注入**，它不是存储而是常驻成本。所以按「读到它的代价」分层：

| 层 | 放什么 | 何时进入上下文 |
|---|---|---|
| **全局 AGENTS.md**（`global + always`） | 用户对做事和表达方式的跨项目要求（按用户的决定，全部在这里）、损失无法挽回的陷阱，必要时附「细节见 X」的指针 | 每轮，所有项目 |
| 全局按需库（`global + on-demand`） | 任何项目都成立、但只在特定场景才用的知识 | 索引行每轮（所有项目）；正文在召回命中时 |
| 项目库（`project + on-demand`） | 本项目代码里看不出的进行中决定与期限、仓库外资源、踩过的坑、还没定成规则的想法；**不存规则**（规则以 AGENTS.md 为准） | 索引行每轮（本工作区）；正文在召回命中时 |
| 项目 AGENTS.md / skill / README | 仓库里的规则、操作流程、给人看的说明与设计取舍 | 宿主加载或模型按需读（插件不写） |
| 不记 | 代码、git 历史、文档里已有的；只为当前任务服务的指令、进度、中途结论 | 永不 |

> 旧版这里是「准入五条（同时满足才进 AGENTS.md）」：跨项目成立、不能从代码推出、违反代价大、能写成动作、
> 已发生 ≥2 次或单次代价极高。它原本只为 AGENTS.md 防膨胀，后来被整体搬去管所有写入，对 `user` / `feedback` / `reference`
> 过严——用户的纠正只说一次也该记。现在「常驻与否」由 `load` 单独决定，「记不记」由各类型自己的门槛决定
> （见「什么值得记：提示词分层」）。

**硬约束**：`maxAgentsBytes`（默认 10000）。超了**拒写**并报当前字节与上限，
逼着先合并或删除——否则「记一条教训」的边际成本看起来是 0，实际每轮都在付费。
拒写文本同时提醒：只在部分场景需要的知识应该用 `load: "on-demand"`，不该进这里。

## 记忆库的查重与覆盖（`supersedes` / `newMemory`）

项目记忆只在 slug 相同时覆盖，slug 不同就并存。于是「本地脚本是兜底」和
「本地脚本已关闭」会同时躺在库里——**召回读到哪条全看分数，比没有记忆更糟**。

所以 `memory_remember` 写入前会查重（复用检索的打分，但**不计 hits**）：

| 情况 | 行为 |
|---|---|
| 库里没有相近条目 | 直接写入 |
| 有候选 ≥ `duplicateThreshold`（默认 0.62） | **拒写**，返回候选清单与分数 |
| 传 `supersedes: "<id>"` | 覆盖那条：旧正文归档到 `history/`，新条目记 `supersedes: <旧 id>` |
| `supersedes` 且新 slug 与旧 id 相同 | **原地更新**：旧版进 `history/`，保留 `created` / `hits`，不再生成 `-2` 副本 |
| `supersedes` 是多条记忆的共同前缀 | **拒写**并列出候选（以前静默取最近一条删掉） |
| `supersedes` 是另一个库里某条的**精确 id** | 跨库取代：先用 `moveMemory` 把旧条搬进目标库（源库留档），再按同库取代处理 |
| `supersedes` 在本库没命中、在另一个库里只按前缀命中 | **拒写** `supersedes-ambiguous`，列出候选与各自所在的库，要求带精确 id 再来 |
| 进待确认 + `supersedes` | 草稿里记下 `supersedes`，收下时才执行取代（同样可以跨库） |
| 常驻写入 + `supersedes` | 草稿里记下旧条与所在库；收下时先写 AGENTS.md 章节，写成功后再归档删除旧条（见「常驻草稿取代旧条」） |
| 传 `newMemory: true` | 确认是独立的一条，照常写入 |

不做自动合并的理由和 AGENTS.md 那套一样：语义重复判断不准。
`duplicateCheck: false` 可整体关闭。

几条与两个库相关的规则：

- **查重同时比对两个按需库**，候选标出 `[project]` / `[global]`：跨项目的规则落进项目库、之后又在全局重复一份，是审计里的真实情况；
- **查重在分流之前**：进待确认的写入同样不能堆出同主题的条目；
- **跨库取代与面板换库共用 `moveMemory`**（官方 user-actions.md：面板能做的数据操作，工具也要能做，且共用一个实现）。
  以前另一个库命中时拒写、让模型换 scope 重来，但模型要的就是「新内容放在这个库、旧的那条作废」；
- **跨库只认精确 id，前缀匹配只在库内用**：第一次审查发现，跨库也接受唯一前缀时，往项目库写一条 `supersedes` 只写了个短前缀的记忆，
  就能把全局库里一条不相关、恰好以它开头的记忆搬走删掉。两个库的精确 id 优先于任何前缀匹配；收下带 `supersedes` 的草稿时同样只认精确 id；
- **两个按需库之间 id 不重复**：定一个新 id 时（新建、换 slug 的取代、收下草稿、面板改名）同时避开另一个库，
  处理方式与库内重名相同（加 `-2`）。面板按 id 选中条目，两个库同 id 时会同时高亮两行、第二条打不开；原地更新保持原 id。

## `paths` 触发提示：按文件把记忆带到眼前

写入时标注的 `paths` 以前是纯摆设——写的时候能标，读的时候没人看，
「什么时候该 recall」只能靠模型自己想起来。

现在读/改到命中 `paths` 的文件时，工具结果末尾会多一行：

```
[记忆] 这个文件有相关记忆（需要细节时调 memory_recall）：
- no-explanatory-text-in-ui — 界面里不要自行添加解释性文字
```

三条克制：

| 约束 | 原因 |
|---|---|
| 只给 id + 标题，**不给正文** | 正文一附上，每次读文件都在付 token 税；要看细节调 `memory_recall` |
| 同一轮同一条**只提示一次** | 读 10 个文件不该重复喊同一句话 |
| 异常/不命中一律放行原结果 | 提示是锦上添花，不能拖垮工具调用 |

匹配规则（按路径**段**比较，不做子串匹配）：

- 相对工作区根书写，判据是「真实路径的末尾若干段与模式逐段相符」，所以绝对路径也能命中
- `*` 只在一段之内通配；`**` 匹配零到多段
- 目录形式（`foo/`）匹配其下所有文件；`src/` 不会再命中 `mysrc/`
- 只写文件名（`client.js`）时匹配任意目录下的同名文件
- Windows 上不分大小写
- 花括号展开（`*.{ts,tsx}`）不支持

实现走宿主的 `tools/post-execute` waterfall（可 enrich 工具结果），
只在工具参数里的 `file_path` / `path` 等字段上判断——不猜、不做语义检索。
两个库都查（项目库在前），全局按需库的条目后面标「（所有项目）」。
`pathsHint: false` 可关闭。

监听器按官方契约写（tools.md「tools/post-execute」、practices.md「Stability」）：它不拥有决策，所以**始终经过 `next()`**。
不需要提示时直接 `return next()`；需要提示时先 `await next()` 拿到下游的决定，只在下游接受、且没有换掉 `value` 时，
在 content 末尾加一块提示，返回值**不带 `value` 键**（content 与 value 只能二选一）。下游拦截了就原样交回。
以前命中时不调 `next()`，会跳过其它插件的后置监听器，而且返回值同时带了 content 与 value。

## 体量与条数预算：成本发生在哪，就在哪设限

| 成本 | 什么时候付 | 策略 |
|---|---|---|
| **条数**（`MEMORY.md` 索引每轮注入，一条一行摘要） | **每轮请求** | `maxMemoryCount`（默认 50）**硬限**，满了拒写；两个按需库分别计数 |
| **全局按需库的索引**（在每个项目的每一轮注入） | **每轮请求，所有项目** | `globalIndexMaxLines`（默认 60）只注入前 N 行，超出写警告 |
| **单条正文长度** | 只在 `memory_recall` 命中的那一次 | `warnBodyChars`（默认 2000）**只提醒，不拦不截** |
| **一次召回的总体积** | 特定调用 | `recallMaxChars`（默认 12000）收敛「返回几条」 |

**为什么不截断长正文**：正文不是每轮成本，只在真正召回到它时才进上下文。
内容确实需要长，就该长——截断等于直接丢信息。所以超阈值只是提醒
「可以考虑拆成 2-3 条原子记忆」，存进去的和传进去的一模一样。

**库满时拒写的返回**里带淘汰候选，按「hits 最少、最久没读」排序——这是现有数据里
最接近「该删」的信号。提示里给两条出路：`supersedes: "<id>"` 合并进去，
或先删一条；确实都值得留就调高 `maxMemoryCount`。

## 依赖解析

插件以 link 方式装进 profile 时，Node 会按真实路径（工作区目录）解析依赖，看不到 profile 的 `node_modules`。

`leanvec`（向量检索，可选）走**三级**解析：

1. 常规模块解析
2. **插件自有依赖目录** `~/.dsh/dsh-workspace-memory-deps/node_modules/leanvec`
3. `~/.dsh/profiles/<name>/node_modules/leanvec`

三级都找不到就降级为纯关键词检索——这是设计内的正常分支，不是故障。

**为什么需要第 2 级**：`leanvec` 曾声明在本插件的 `optionalDependencies` 里，但 pnpm **不保证为 link 目标安装依赖**，
用户下一次 `pnpm install` 就把它剪掉了，向量检索**静默退化**成纯关键词（实测发生过一次）。
自有依赖目录不受 profile 依赖图影响，用 npm 装：

```bash
node scripts/install-deps.mjs   # 一次性，约 85 MB，装到 ~/.dsh/dsh-workspace-memory-deps
```

装完重载一次插件即可切到向量模式。`memory_status` 会显示当前是 `hybrid` 还是 `keyword`。

## 召回质量怎么衡量：金标集 + 负样本

`eval/golden/` 放语料与查询集，`eval/golden.mjs` 跑分，`test/golden.test.mjs` 把门槛写进 CI。

| 指标 | 含义 | 当前基线 |
|---|---|---|
| recall@1 | 第一条就命中期望记忆 | 70% |
| recall@3 | top-3 内命中 | 90% |
| MRR | 命中排名的倒数均值 | 0.80 |
| **负样本误召** | **库里没有答案时，返回了东西的比例** | **0%** |

负样本是最容易被忽略的一半：只测正样本的话，「随便返回点什么」也能拿高分。
本插件最初的判据是「向量分或关键词分过线就入选」，实测负样本误召 **100%**——
leanvec 是静态嵌入，任意文本余弦都容易过 0.3，等于没有闸门。因此引入了融合分闸门
`minScore`（默认 0.34，由 `eval/sweep-min-score.mjs` 扫出来）。

阈值是**在 18 条样本上**调的，且 0.33→0.34 之间误召从 13% 直接跳到 0%，
是个陡崖。真实语料变大后应重跑扫描再定，不要把它当成普适常数。

三份评测量的是不同环节，不能混为一谈：

| 脚本 | 量什么 | 怎么跑 |
|---|---|---|
| `eval/golden.mjs` | **召回**：记下的能不能找回来（本节） | 纯本地，可进 CI |
| `eval/remember.mjs` | **写入主路径**：对话里模型会不会主动调 `memory_remember`、记到哪、记成什么样（下一节） | 调模型，手动跑 |
| `eval/run.mjs` | **自动抽取**这条默认关闭的旁路：precision / recall，分「全部入队」与其中「已核实」两组报，并按已核实 / 未核实 / agent 计数（口径与插件一致：核对不过不丢弃） | 调模型，手动跑 |

## 写入怎么衡量：主路径评测

`eval/run.mjs` 只评自动抽取这条默认关闭的旁路；真正天天在用的，是模型在对话里主动调 `memory_remember`。
写入准入改来改去，没有这份评测就只能说「感觉好点了」。

`eval/remember.mjs` 模拟一次对话进行到某一刻。每个场景一个独立的假宿主和临时目录，真实 `apply` 插件；
模型真实调用插件注册的 `memory_remember` / `memory_recall`，证据核对、分流、查重都走真代码，全部写进临时目录。
其余工具（读写文件、编辑、跑命令、todo）操作一份内存里的虚拟项目，读写与常见命令有一致的输出。
提示词按宿主的摆放方式拼：系统提示段进 system prompt，动态 context 包成一条 user 消息插在对话之前。

- **场景** `eval/remember-cases.json`：52 个合成场景，dev 31 / test 21（test 留作最终检验，`--split=dev` 时不跑也不输出）。
  类别：用户纠正做法或表达、项目决定与期限、仓库外资源、用户是谁、负样本、模型自己踩的坑、归宿是 skill / AGENTS.md / README、
  有长期信号但去向不明、更新已有记忆。
- **指标**：处理率、漏记数、误记数、归宿正确率、字段正确率、证据核对通过率、写入分布、红线命中、截断数、首轮 prompt token。
  步数用尽、且此前没有写记忆或写文件动作的运行记为截断，不进处理率、漏记、误记、归宿的分子分母。
- **新旧两版都能测**：`--index` 指向另一份 `index.js`。旧版没有 `source` / `load` / `evidence`，相关约束记「不适用」。

```bash
node eval/remember.mjs --split=dev --max-requests=<N>                  # 测本仓库的 index.js
node eval/remember.mjs --index=<另一份>/index.js --split=all --out=<结果.json>
node eval/remember.mjs --only=<场景 id,…> --keep                        # 只跑几个场景，保留临时目录
node eval/remember.mjs --rescore=<结果.json>                            # 不发请求，按当前计分规则重算
node eval/remember.mjs --resume=<结果.json> --index=<同一个插件>          # 只补跑缺失或失败的场景，合并回同一个文件
node eval/remember.mjs --replay=<结果.json> --index=<要测的 index.js>     # 离线重放：不发请求、不读凭据（见下）
node eval/remember.mjs --export-prompts=<目录> --index=<插件> --split=dev  # 导出每个场景第一步看到的提示（不含答案），交给别的模型作答
node eval/remember.mjs --import-decisions=<目录> --index=<插件> --split=dev --out=<明细.json>  # 读回答案，真实执行并计分
```

| 参数 | 作用 |
|---|---|
| `--index` | 测哪一份 `index.js`，用来对比新旧版本 |
| `--split` | `dev`（默认）/ `test` / `all` |
| `--only` | 逗号分隔的场景 id |
| `--max-steps` | 每个场景最多几步，默认 16；前后对比必须用同一个值 |
| `--max-requests` | 本次最多发多少个模型请求（含重试），到了上限就不再发，正常写结果；默认不限 |
| `--rescore` | 对已保存的结果离线重算，不发请求 |
| `--resume` | 只补跑结果文件里缺失或请求失败的场景，先备份再合并；`--index` 与文件记录不一致时拒绝执行 |
| `--replay` | 把结果文件里真实模型写出的记忆工具调用原样重放到 `--index` 的插件上，逐次对比新旧结果；完全离线，可加 `--split`、`--out` |
| `--export-prompts` | 把每个场景模型第一步看到的全部信息（系统提示、工具定义的 JSON Schema、对话）导出成 `<id>.md` 加 `manifest.json`；文件里没有标准答案与任何分类信息；不发请求 |
| `--import-decisions` | 读回每个场景的一份答案 `<id>.json`（`{"tool_calls":[…],"final_reply":"…"}`），在全新的场景宿主里按顺序执行（记忆工具走插件真代码，其余走虚拟项目），按同一套规则计分；不发请求 |

`--rescore` / `--resume` / `--replay` / `--export-prompts` / `--import-decisions` 一次只能用一个。模型、网关、凭据、并发、温度、超时等其余参数见脚本文件头。

**同一时间只跑一个评测进程，并且设 `--max-requests`。** 评测会消耗模型额度；两份评测并行时共用同一份额度，
曾在中途把评测所用模型账户的额度用尽，两份都没跑完。要比较两版，就先跑完一份再跑另一份，不够再用 `--resume` 补。

**评测环境本身返工过三次**，留下的教训：

1. 固定回复的假工具会让模型反复试探环境，测到的是「模型怎么对付一个假环境」——所以换成了状态一致的虚拟项目；
2. 步数太少会在任务收尾前截断，而「记不记」恰恰发生在收尾——默认步数从 8 提到 16（脚本注释：一件小活就要 9–14 步），截断的运行单独计数；
3. 不要用「最后一步只开放记忆工具」来强制收尾：那等于暗示模型去记，测出来的处理率是假的。

### 离线重放：`--replay`

**为什么要它。** 模型额度用尽之后，后面几轮的改动没法在模型上验证；但之前的运行里存着模型给出的每一次工具调用。
重放把这些**真实模型输出**原样喂给新版本，检验新版本的**代码路径**——证据核对、相关性判断、分流、查重、返回文案——
在真实写法上表现如何。

**怎么做**（实现在 `eval/lib/remember-replay.mjs`）：对结果文件里每个已完成的场景，用 `--index` 指定的插件建一个全新的场景宿主
（与原运行同样的预置数据和用户消息）；先照真实宿主的顺序，对每条用户消息触发一次 `agent/pre-step`，让「用户原话」缓存与快照回落两路都有数据；
再按原顺序把当时模型给出的 `memory_remember` / `memory_recall` 调用原样重放（入参不补不改，通用工具跳过），记录新返回并与原结果逐次对比。
计分沿用现有规则：写入结果与库的状态取重放，模型的最终回复、文件写入、是否用尽步数取原运行——这些不随插件变。
对 `source: user` 的写入，还分别用 [标题, 摘要, 正文] 与只用 [标题, 摘要] 各算一次相关性，看正文对判断有没有贡献。

**局限。** 重放**不重新采样模型**：入参全部来自旧运行，所以它检验不了新提示词、新 schema 会不会让模型换一种写法、换一个去向——
那只能等真跑。它也只能覆盖旧运行里实际出现过的写法：旧运行没走到的场景类别、没出现过的证据形态，重放同样看不到。

**先自检。** 把一份记录重放到它**原本对应的那个版本**上，结果必须逐次一致；不一致说明重放本身（宿主的搭法、消息顺序、计分）有偏差，
这时对新版本的重放结果不可信。2026-11-14 的自检：14 次写入、4 次召回、9 个场景的主结果全部一致，另一份 3 个场景的记录同样全部一致。
对第六轮定稿版本的重放结果见 HANDOFF 25.5（重放早于代理模型评测驱动的那一轮，「调用时必须归类」不在重放过的代码里）。

### 代理模型评测：`--export-prompts` / `--import-decisions`

**为什么要它。** 目标模型的额度用尽后，后几轮的**提示词**改动没法在目标模型上重新采样；离线重放又只能检验代码路径。
为了让新提示词至少被某个模型重新采样一次，把「生成答案」从脚本里拆了出去。

**怎么做。** `--export-prompts` 把每个场景在第一步会看到的全部信息导出成一个自包含的文件（没有标准答案）；每个场景交给一个
**全新的、只见过这一个文件的小模型**独立作答（不是目标模型），答案是一份 `{"tool_calls":[…],"final_reply":"…"}`；
`--import-decisions` 把答案读回来，记忆工具调用放进插件真实执行，其余工具走虚拟项目，再用同一套规则计分。
改动前与改动后的提示各导出一遍，得到**同一个代理模型下的成对比较**。提示词的迭代只看 dev 组，test 组留作检验。

**局限（全部）：**

- 代理模型不是目标模型，绝对数字不能套用到目标模型上，只适合比较「同一个模型拿到新旧两套提示」；
- **单步作答**：模型一次给出整轮的工具调用和最后一句话，看不到任何工具返回。被拒后重试、被改道后是否真的向用户提议，都测不到；
- 模型看不到仓库内容：`edit_file` 因为对不上原文而失败、或者模型先 `read_file` 再说「读完后修改」，都会被记成「什么都没做」。
  归宿类场景（要改 AGENTS.md / README 的）因此被自动打分**低估**，必须人工读答案；
- 每个场景只采样一次，同一场景在两次采样之间会翻转。只有「同一类场景整体翻转」才算信号；
- 归类靠关键词启发式，会漏判（例如「放在项目文档里」没被认作提议）；
- test 组一共跑了两次（第三版一次、最终版一次）。第一次的结果被看过；虽然没有针对 test 组的判错去改任何东西，第二次已不算严格的留出集。

## 什么时候触发召回：三个触发点

「记下来」只是第一步，能不能在**该想起来的时候想起来**才是关键。本插件有三个触发点：

| 触发点 | 实现 | 给什么 |
|---|---|---|
| **每轮固定** | `system-prompt/context` 注入两个库的 `MEMORY.md` 索引 | 全部条目的「一行摘要」（全局按需库至多 `globalIndexMaxLines` 行） |
| **碰到文件** | `tools/post-execute` 比对两个库的 `paths` | 命中文件的 id + 标题 |
| **用户发消息** | `agent/pre-step` 里预取，两个库一起查、按分数合并 | 与本轮请求最接近的 3 条 id + 标题 |

后两个都只给 id 与标题，正文一律要 `memory_recall` 取——这是渐进式加载的底线。全局按需库的条目只有经这三条路才会出现，
其中预取是它最主要的入口；出现时标「（所有项目）」。

这三个触发点管的是「想起来」。「想到要记」靠的是系统提示段（见「注入」与「什么值得记：提示词分层」）。

**预取为什么绕这么一圈**：注入用的 `context.text` 是**同步**的，拿不到用户消息；
而 `agent/pre-step` 是 async waterfall 且带 `messages`。所以在 pre-step 里 `await` 一次
真正的 recall（用的就是金标集标定过的 `minScore`），把结果缓存起来，注入时只读缓存。
**不往 messages 里塞合成消息**——那会污染对话记录。

预取的查询也只用人写的文本（与证据核对同一个 `humanTextOf` 口径）：以前整批消息拼起来查，注入的上下文也混进了查询。
同一个 pre-step 监听还把本批消息里人写的文本收进进程内缓存，作为证据核对的主路径（见「证据核对」）；
关掉 `prefetchRecall` 不影响这件事。这个监听不拥有决策：始终 `return next()`，只调一次，两件事各自 try/catch，任何失败都不挡步骤。

预取在回合结束时清空，不会让上一轮的相关记忆污染下一轮。`prefetchRecall: false` 可关闭。

## 什么值得记：提示词分层

「该不该记」没法用代码判定，硬拦会误伤——"改成 X" 有时确实是长期约定。所以这一层是**策略，不是过滤器**：
判据靠提示词，代码只做确定性的护栏。

> 2026-11-14 前，全部判据（「五条准入」、不记什么、写入与更新时机）写在 `memory_remember` 的 description 里，
> 抽取提示词另有一套说法。现在按官方插件开发说明分三层放，判据也从「五条全满足」换成了按类型的门槛。

### 三层各放各的，同一条规则只出现一处

依据官方 practices.md「Add prompt text with `ctx.systemPrompt.section()`」与 tool-design.md「Say each fact once」
「Put parameter rules on the parameter」「Describe behavior, not implementation」：

| 层 | 常量 | 放什么 |
|---|---|---|
| 系统提示段（静态） | `MEMORY_SECTION` | 归宿怎么判断（流程先按形态；规则以 AGENTS.md 为准；跨项目的「用户是谁」与偏好进全局 AGENTS.md；其余进记忆）；「这次」不记；用户纠正时要做的两件事、只纠正结果时不归纳做法；没调用工具前不说「记下了」；共享文件先说明再写、等答复期间不先存一份；拿不准就问、没有具体要记的不泛泛地问；自己验证过的坑直接存；记忆写的是当时的情况，照做前先确认 |
| `memory_remember` 的 description | `REMEMBER_DESCRIPTION`（含 `WORTH_SAVING`） | 只写做什么、何时用、返回什么：用 `type` 说明这是什么（三类非记忆会被告知去处）；值得记与不值得记各一句；显式要求或纠正时立即写，其余在任务结束时写；改已有记忆用 `supersedes` |
| 参数说明 | `TYPE_RULES`、`BODY_RULE`、`SOURCE_RULE`、`EVIDENCE_RULE`、`SCOPE_RULE`、`LOAD_RULE`、`DESCRIPTION_RULE`、`SLUG_RULE` 等 | 每条规则挂在它管的那个参数上 |

动态 context 只放会变的事实（两个库的索引与预取结果），不放任何行为指引。
抽取提示词 `EXTRACTION_SYSTEM` 是另一次独立的模型调用（看不到工具 schema，也看不到系统提示段），由同一批常量拼成，
另带一份英文的四个归宿 `HOMES`，所以口径只有一份。

**为什么行为指引放系统提示段。** 审计里漏记时，模型的推理里一次都没考虑过写记忆；而当时每轮注入只讲召回，库为空时什么都不注入——
写入没有触发点。「什么时候想到要记、记到哪」是不随轮次变化的行为指引：放在静态段里可以被前缀缓存复用，也不依赖「库里有没有东西」。
这一段对所有 agent 都一样，包括没有记忆工具的子 agent：组装系统提示时拿到的上下文里没有工具集信息，无法区分（见 HANDOFF 25.4）。

### 系统提示段的设计（最终文本以 `MEMORY_SECTION` 为准）

系统提示段先在代理模型上迭代了三版（见「代理模型评测」），又按目标模型评测与用户的去处决定改了第四版（第九、十轮）；每一处措辞都对应一个观察到的错误或一条用户的决定：

- **归宿先按形态，其余先问「给谁用」。** 第一版把四个归宿并列列出，没有判断依据，发布流程、仓库规则、设计取舍都被存成了记忆。
  第二版把「给谁用」放在最前，发布流程又被当成「我和用户之间的事」存成记忆。第三版改成：可重复的多步流程先按形态归 skill，
  不管只有助手用还是大家都用；其余的才问「只有你和这位用户用得上」（进记忆）还是「任何进这个仓库的 agent 或接手的人都用得上」（写进仓库）。
  第四版按用户的决定把「其余」拆细：必须遵守的规则以 AGENTS.md 为准（全员的写项目 AGENTS.md、只对用户本人成立的写 AGENTS.local.md，
  「决定仓库里会留下什么的约定」也算，规则不往记忆里存第二份）；在所有项目都成立的「用户是谁」与做事、表达方式的长期要求进全局 AGENTS.md
  （`scope: global` + `load: always`，进待确认）；剩下只有助手和这位用户用得上的才进记忆。「用户是谁」原来列在「记忆」一栏，
  与代码把 `type: user` + `scope: global` 强制常驻不一致，之后挪到了全局 AGENTS.md 那一行。
- **纠正要做两件事。** 原文「都要处理，不要略过」有歧义：当场改正也算「处理了」，于是不带「以后」的纠正没记。现在写明两件事——
  当场改正，并把这条做法记进记忆；并说明「只在回复里答应以后会注意没有用，下次会话不记得这次对话」。
  「以后 / 每次 / 记住 / 默认」这类词只说明要长期保留，去处仍按上面的判断。
- **没调用工具前不要说「记下了」。** 写明没有调用 `memory_remember` 并拿到返回之前，不要对用户说「记下了」；决定先问用户写到哪时，就说明还没记。
  起因是目标模型评测里那一次「嘴上说记下了、其实没调用工具」：模型遵守了「等用户答复期间不要先存一份」，回复里却说成已记下（见「目标模型评测」）。
- **不要先存一份。** 模型提议写仓库的同时，又往记忆里存了一份。现在写明等用户答复期间不要先存，否则同一条内容有两个出处。
- **自己验证过的坑直接存。** 模型曾对自己踩的坑先问一句「要不要记」；现在说明直接存，它会进待确认、由用户决定（这句补上之后**没有再测**）。
- **「这次」不记，只纠正结果不归纳。** 第四版写明话里明确说了「这次」的只管这一次、不记；用户只是指出这次的结果不对（算错了、写错了）时改对就行，
  不要自己归纳出一条做法去记——目标模型评测里出现过后一种。
- **没有具体要记的东西时，不要泛泛地问。** 目标模型评测里，模型在收工时泛泛地问「要不要记一笔」；第四版写明不要这样问。
- **例子不与评测场景重合。** 流程的例子刻意不用评测场景里的那几类，否则等于把考题写进提示词；抽取提示词里的四个归宿（`HOMES`）同样换了例子。

工具说明里也补回了一句「改已有记忆用 `supersedes`，不要另存一条」：代理模型评测里更新已有记忆时新建了一条、被查重拒写——这条以前只写在参数上。

即便如此，提示词只是建议：用户没明说去处的归宿场景，三版提示词下始终不稳，真正让判断变稳的是「调用时必须归类」；
跨项目偏好的 `load` 也一样，写进提示词之后目标模型仍会留在 `on-demand`，最后由代码强制（见「跨项目偏好强制常驻」）。
`LOAD_RULE` 相应改成：偏好（用户对做事和表达的跨项目要求）用 `always`，其余用 `on-demand`。

**为什么规则放在参数上。** 模型在填哪个参数时，就读到管这个参数的规则。全部塞进工具说明时，说明越写越长，
同一条规则又在抽取提示词里有另一种说法，两套口径各自漂移。放在参数上、由常量复用，改一处就是改全部。

**代价：每轮固定进上下文的字符数**（系统提示段 + 四个记忆工具的定义，按发给模型的工具定义 JSON 计）从改动前的 5722 涨到定稿的 **7931**，
多 2209 个字符，**约 39%**。其中系统提示段 999；`memory_remember` 的 description 从 1517 降到 820，各参数说明合计从 2150 升到 3492。
增量分三段：第六轮时是 6681（约多 17%），来自规则从说明搬到参数上、新增 `source` / `evidence` / `load` 各带一条说明；
代理模型评测那一轮到 7516（约多 31%），来自归宿判断与纠正类场景增加的措辞，以及 `type` 的三个改道取值；
第九到十一轮到 7872，来自按用户决定重写的系统提示段（规则以 AGENTS.md 为准、偏好常驻、「这次」不记、不泛泛地问）与改写的 `LOAD_RULE`、`TYPE_RULES`；
之后到 7931，来自系统提示段补的「没调用工具前不要说记下了」与「用户是谁」的挪动。
这是给「写入有触发点、归宿能判对」付的固定成本；目标模型上的对照见「目标模型评测」。

### 各类型的门槛（`TYPE_RULES`，取代「五条全满足」）

- `user`：用户是谁（语言、角色、专长、长期偏好）；只记用户自己说的，不记你对用户的印象；
- `feedback`：用户纠正了你**做事或表达的方式**，或确认了一个非显然的做法；**第一次就记，不等重复**；纠正这次任务的产出（一个错的值、一个笔误）不算，即使能从中引出一条教训；
- `project`：用户说的、代码里看不出的目标、决定、约束、期限；日期写绝对日期；不记你自己的计划或进度，也不记仓库的长期规则（那是 `repo-rule`）；
- `reference`：仓库外的东西在哪（URL、面板、账号、文档）、做什么用；
- `pitfall`：你踩到并**验证过**的非显然的坑，或唯一可行的做法；写明触发场景与失效条件（如某个版本）；猜测或中途的推断不算。
- 三个「不是记忆」的取值：`procedure`（可重复的多步做法）、`repo-rule`（这个仓库里所有人都要遵守的规则）、`docs`（项目是什么、怎么用、为什么这样做）。
  合适就选，工具不保存，而是告诉模型该写到哪。

「五条全满足」对 `user` / `feedback` / `reference` 过严：用户纠正一次表达方式，既不是「已发生 ≥2 次」，单次代价也不大，
按五条就不该记——而审计里漏掉的恰恰主要是这类纠正。

**正文**（`BODY_RULE`）：规则一两句，再写「Why:」「How to apply:」两行；写用户要什么，不写你选来实现它的机制；
不写下周就过期的值——提交哈希、计数、版本号、备份或安装路径（版本号作为坑的失效条件可以）。

**不记**（`WORTH_SAVING`）：当前任务的指令、进度、结果；diff 或文档里已经有的；你对用户的评价；泛泛的建议；密钥与令牌。

**写入时机**：用户显式要求或**纠正**时立即写；其余在**任务结束**时写，不在中途——中途的结论经常被推翻。

**更新时机**：用户改主意、或记录被证明错了，就传 `supersedes`，不要让两条互相矛盾的记忆并存。

### 代码护栏（确定性的部分，都不改内容）

- **入参校验**：`type` / `scope` / `load` 非法值拒写 `invalid-argument`（见「工具」）；
- **归类改道**：`type` 是 `procedure` / `repo-rule` / `docs` 时不保存，返回去处；更新已有记忆时例外（见「调用时必须归类」）；
- **`needs-slug`**：标题含非 ASCII 又没给可用 slug 时拒写，作为必填 slug 的兜底；
- **`paths`**：写得不像路径（如 `"插件配置"`、URL）时，写入结果会点名并给出正确写法——否则那个字段永远静默失效；
- **过期值提示**：正文里像提交哈希（7–40 位十六进制、同时含字母和数字）或版本号（`v?x.y.z`）的值，会在返回里点名，
  不拦截、不改写；`pitfall` 的版本号豁免（版本正是坑的失效条件），围栏代码块里的不检（那是命令或输出样例）。
  审计里 24 条记忆有 13 条规则还对、但混着这类早已过期的值，召回时反而误导。

措辞会在评测里反复改，所以 `test/admission.test.mjs` **只守结构**：各参数的说明就是对应常量；抽取提示词包含同一批常量；
每条规则在「工具说明 + 全部参数说明」里只出现一次；系统提示段不含参数规则；context 不含系统提示段的内容；
工具说明与全部参数说明的长度上限。不断言具体句子。另有一条断言：明显像任务指令的内容也不会被拦——
把「不做内容过滤」这个决定写进测试，免得以后有人加个正则当过滤器。

## 测试

```bash
npm test                        # 全部（node --test 自动发现 test/ 下的文件）
node test/recall.test.mjs       # 单个文件；每个测试都是独立脚本，失败时退出码为 1
node eval/remember.mjs --split=dev --max-requests=<N>   # 主路径评测：调模型、消耗额度，手动跑，同一时间只跑一个
```

测试文件统一用 `*.test.mjs` 后缀，`test/fake-host.mjs` 是路由/工具测试共用的假宿主。**别只挑几个跑**：曾经因为冒烟测试叫 `smoke.mjs`、
循环里拼成 `smoke.test.mjs`，被误判成「PowerShell 退出码不可靠」查了三次。
`npm test` 现在发现 40 个文件：37 个 `*.test.mjs`，加上 `node --test` 一并发现的 3 个辅助模块（`fake-host.mjs`、`isolate-home.mjs`、
`relates-samples.mjs`，被发现时只是空跑）。

**测试隔离：`test/isolate-home.mjs` 必须是测试文件的第一个 import。** 它把 `DSH_HOME` 指到本测试文件独占的临时目录，
进程退出时恢复环境变量、删掉临时目录。ESM 的静态 import 按顺序先于模块体执行，所以它一定在测试里 `await import('../index.js')` 之前生效。
为什么需要它：第一次审查在「模拟的真实主目录」下复现过——有的测试用 `configure()` 而没传 `globalMemoryDir`，默认路径落到真实主目录，
在已启用全局库的机器上会读到、甚至搬走真实条目。另外两点：

- 原来的 `DSH_HOME` 记下来交给 `realFilesGuard()`，在「模拟的真实主目录」下跑测试时，那个目录一个字节都不能变；
- 嵌入模型（leanvec）在切换之前解析一次并缓存：它装在主目录下，不这样做所有测试都会退化成纯关键词检索，金标集与预取的断言会因为环境而变。

目前只有 `test/client-logic.test.mjs` 不 import 它：那个文件只读 `client.js`，不加载 `index.js`、不碰任何主目录路径。新增测试文件时，
只要会加载 `index.js`，第一行就是 `import './isolate-home.mjs'`。第六轮定稿时 `npm test` 在两种环境下都全绿：正常环境，以及 `DSH_HOME` 指向模拟主目录；
加上 `test/routed-types.test.mjs`（三个改道取值与「更新留在原处」）之后的 40 个文件，在正常环境下全绿。

所有测试只在临时目录里读写。涉及 AGENTS.md 或全局按需库的测试仍然经 `apply(ctx, { agentsFile: 临时路径, globalMemoryDir: 临时路径, ... })` 传配置，
并前后比对真实文件（`test/fake-host.mjs` 的 `realFilesGuard()` 对主目录下的 AGENTS.md 与全局按需库算哈希）——隔离与快照比对是两道独立的保险。

两次独立审查的每一项发现都有对应的反例测试：`test/review-fixes.test.mjs`（第一次）、`test/review2-fixes.test.mjs`（复审）；
`test/relates-samples.mjs` 是相关性判断的实测样例（22 条纠正、无关回复、绕过样例）。

## 配置

所有可调项都写在插件行的 `config` 里，改完重载插件生效。

**没有声明 `export const Config`**（那需要 `@deepseek-ai/schemastery`，对 link 安装的插件未必能解析到），所以 Settings 面板不会渲染成表单，但值会生效并被校验；校验问题通过 `memory_status` 暴露。

```yaml
- id: dsh-workspace-memory
  name: dsh-workspace-memory
  config:
    enableExtraction: true      # 打开回合收尾自动抽取
    extractEveryTurns: 5        # 每 5 回合抽一次
    minVectorScore: 0.35        # 调严召回门槛
```

| 键 | 默认 | 说明 |
| - | - | - |
| `memoryDir` | `''` | 空 = `~/.dsh/projects/<编码后的工作区路径>/memory/`；非空必须是绝对路径或 `~/` 开头，且受下面的目录限制 |
| `globalMemoryDir` | `''` | 全局按需库目录。空 = `~/.dsh/dsh-workspace-memory/global/memory/`；非空必须是绝对路径或 `~/` 开头，且受下面的目录限制 |
| `indexMaxLines` / `indexMaxBytes` | 200 / 25KB | 项目库索引的注入上限 |
| `globalIndexMaxLines` | 60 | 全局按需库索引每轮最多注入几行（0–200）；`0` = 不注入 |
| `weightVector` / `weightKeyword` | 0.65 / 0.35 | 融合权重 |
| `minScore` | 0.34 | 融合分闸门（金标集标定，见「召回质量」） |
| `minVectorScore` / `minKeywordScore` | 0.3 / 0.5 | 前置筛（任一达标才进入融合打分） |
| `recallMaxChars` | 12000 | 一次召回的正文总预算（少带一条，不截断正文） |
| `maxTitleChars` / `maxBodyChars` | 200 / 20000 | 格式闸门 |
| `maxTags` / `maxTagChars` | 20 / 40 | 格式闸门 |
| `maxMemoryCount` | 50 | 每个按需库的条数硬限，满了拒写；`0` = 不限 |
| `warnBodyChars` | 2000 | 单条正文的提醒阈值（不拦不截） |
| `agentWrites` | `review` | 模型自己得出（`source: agent`）的按需写入：`review` 进待确认，`direct` 直写；`load: always` 不受影响，永远进待确认 |
| `duplicateCheck` / `duplicateThreshold` / `duplicateCandidates` | `true` / 0.62 / 3 | 写入前查重（两个按需库一起比） |
| `pathsHint` / `pathsHintLimit` | `true` / 3 | 碰到文件时的记忆提示 |
| `prefetchRecall` / `prefetchLimit` | `true` / 3 | 用户消息预取 |
| `enableExtraction` | `false` | 回合收尾自动抽取 |
| `extractEveryTurns` | 5 | 抽取节流 |
| `extractMaxPerTurn` | 3 | 单次最多入队几条 |
| `dedupeThreshold` | 0.9 | 与已有记忆/待确认条目的余弦相似度超过它就不入队 |
| `historyLimit` | 20 | 每条记忆保留多少个历史版本；`0` = 不留档 |
| `agentsFile` | `''` | 空 = `~/.dsh/AGENTS.md` |
| `maxAgentsBytes` | 10000 | AGENTS.md 字节上限，超了拒写（缩小的编辑始终允许）；`0` = 不限 |
| `editorExe` | `''` | 打开 AGENTS.md 用的编辑器；空 = 自动探测 |

坏值**不会抛异常**：退回默认值并记录 issue（`memory_status` 可见）。一个配置笔误不该让整个记忆系统不加载。
`agentWrites` 只接受 `review` / `direct`，其它值同样回落默认并记 issue，不会被当成别的值。

**库目录的限制**：`memoryDir` / `globalMemoryDir` 不能是 DSH 主目录或它的上级、不能是宿主的共享 agents 根（`$DSH_AGENTS_HOME`，
没设时是 `~/.agents`）或它的上级，也不能就是 AGENTS.md 所在的目录；违反时记 issue 并回落默认目录。原因：库目录里的 `*.md`
都会被当成记忆列出来，第一次审查复现过把 `globalMemoryDir` 设成主目录后，AGENTS.md 被当成一条记忆、能被 `memory_forget` 或面板删掉。
共享 agents 根是复审补上的：宿主同样从那里加载用户级 AGENTS.md（官方 dsh-home-paths）。插件只拿它做这项检查，不读写它。
`enableDiagEndpoint` 已移除（诊断端点随客户端回执一起删掉了），旧配置里留着它只会被当作未知键忽略。

`directWriteConfidence`、`minExtractConfidence` 已于 2026-11-14 废弃（分流改为按来源）。配置里留着它们不会生效，
config issues 里会出现一条废弃提示，指向 `agentWrites`——而不是一句「未知配置项」，让人以为自己拼错了。

## 历史版本与命中计数

记忆是**纯 Markdown、没有 git 兜底**，改错一次就永久丢失。为此：

- **覆盖或删除前留档**到 `.memory-state/history/<slug>/<时间戳>.md`，只保留最近 `historyLimit` 版
- 只有**实质内容变化**才留档——`modified` / `hits` / `lastHit` 每次都会变，先剔除再比较，
  否则历史会变成一堆没意义的版本
- 回退方式很直接：把历史文件拷回 `memory/<slug>.md`，再 `/memory reindex`

**命中计数**：被 `memory_recall` 召回的条目会在 frontmatter 里累加 `hits` 并写 `lastHit`。

- **只改这两行**，文件其余部分逐字节不动（以前整份重写，手写的 YAML 块列表、注释会丢，每次还多一个空行）
- 计数器**不重建 MEMORY.md**（命中不进索引），也**不留历史**（属于元数据抖动）
- 只对**真正返回给调用方**的条目计数，未命中的不涨
- `modified` 不会被命中改动——语义内容没变

它的用途是回答「哪些记忆该淘汰」：长期 `hits = 0` 或 `lastHit` 很久以前的条目，
就是候选。没有这个信号，记忆只会越攒越多。

## 自动抽取与待确认队列

抽取挂在 `agent/turn-stopping`——官方为「回合即将结束」留的 serial 座位，每回合都触发。

> **为什么不是「压缩前」**：本 profile 的 `compaction-basic` 是 `inactive`，没有压缩实现，
> 「压缩前触发」永远不会发生；事件目录里也没有「压缩前」这个位。
> 这是实测后从原方案改过来的。

```
agent/turn-stopping（serial，会被 await）
  → 每 N 回合才真跑（默认 5）            成本闸门
  → 取本轮 user/assistant 文本            只取人写的用户消息；工具结果不取：费 token 且几无价值
  → ctx.llm.stream 用会话当前路由的模型    不额外配 provider；接上回合的取消信号
  → parseExtractionJson                  容忍 ```json 围栏与前后闲聊
  → 证据核对                              source: user 时核对出处与相关性，结果记进 evidenceVerified
  → 向量去重                              与两个按需库的已确认记忆 + pending 一起比
  → 写入 pending/<id>.md，status: draft
```

**默认关闭**。它会给每回合加一次模型调用，而且这个监听会被 `await`。任何环节失败都只记录、不冒泡——抽取是旁路，永远不许影响主对话。

- 抽取提示词与 `memory_remember` 的参数说明由同一批常量拼成（见「什么值得记：提示词分层」），只抽归宿是记忆的条目
- 抽取结果一律进待确认，不按来源直写（自动积累，但不让模型自作主张）。证据核对与 `memory_remember` 同一套（出处 + 相关），
  **核对不过的不丢弃**，以「未核实」身份入队（`evidenceVerified: false`），面板不会把它标成「用户原话」。
  以前核对不过就丢：抽取本来就只进待确认，丢掉等于替人做了决定，而相关性判断会误判改述式的真实纠正。
  核对用的是**全会话**的用户消息，而不是送给模型的那 6000 字尾部——用户的纠正可能在很早之前
- 去重同时比对全局按需库：跨项目的规则已经在全局库里时，不该再从每个项目各抽一份（以前只比项目库）
- 抽取不能提问，`project + always` 的候选降成按需入队：面板只能收下或丢弃草稿、不能改它，但按需去向的影响面小，比丢掉稳妥
- 跨项目偏好的强制常驻同样适用：`type` 为 `user` / `feedback` 且 `scope: global` 的候选按常驻入队（收下后进全局 AGENTS.md）
- 抽取不能向用户提议写仓库，所以 `type` 是 `procedure` / `repo-rule` / `docs` 的候选直接跳过并计数
- 用户中止回合时抽取立刻停下、不入队；超时则用已收到的部分（那是「模型慢」，不是「用户不要」）
- `/memory extract` 报告「候选 N 条 → 入队 a 条（其中 c 条以未核实身份入队）、去重丢弃 b 条」，有跳过的非记忆候选时一并报出条数

`pending/` 里的条目**不注入、不参与检索、不进 MEMORY.md**，只有 accept 之后才搬进正式库。

- 草稿 id 是 `dr_<时间>_<随机后缀>`：同一批候选在同一毫秒落盘时，只用时间戳会互相覆盖
- 模型回复里候选正文带代码围栏、或前后夹着闲聊，都能正确解析；回复被截断时返回空，不猜
- 抽取流有 60 秒墙钟上限，模型卡住时不会拖住回合收尾
- 收下时受 `maxMemoryCount` 约束（取代旧条除外），满了返回 `library-full`，草稿留在队列里
